- 2026-08-09 v5.51: **B8-2「返金」を新設した。** これまで返金の扱いは仕様書に一行も無く、返金されてもコインもキャラも残っていた。買って、使って、返金する、を繰り返すだけでただで使える状態であり、課金でいちばん大きい穴だった。返金の申請はストアの画面から利用者が行うもので、アプリからは申請できず止めることもできない。こちらがやるのは知らせを受けて後始末をすることだけである。返金は解約の申し出と同じ種類の知らせ（`CANCELLATION`）で届き、理由の欄が `CUSTOMER_SUPPORT` のものが返金である。買い切りにも届くので、月額の商品だけに絞る判定より前に見分ける。コインは残っているぶんを消し、足りないぶんは未精算として持ち越して**残高をマイナスにする**。使い切られていても取り返しにはいかない。マイナスの間は通話も送信もできず、**毎日の無料コインからだけ**差し引いて0になるとまた使える（買い直したコインから引くと払ったぶんまで取り上げることになる）。買ったキャラは話せない状態にし、**その場では消さず14日置く**。返金2回で購入できなくし、回数そのものは画面に出さない。入れ直しによる周回はv1では止めない（Androidに規約上きれいな手段が無く、止めるにはログインが要る）。あわせて**返金の取り消し**（`REFUND_REVERSED`。Appleのみ）を定めた。Appleの資料に「返金を理由にコンテンツやサービスを取り上げた場合は、元に戻す必要がある」と明記されており、扱わない選択は無い。取り消せる期間は書かれていない。コイン・未精算・返金の回数・キャラの所有を戻し、未精算がすでに無料コインで埋まっていたぶんはコインとして返す。14日以内なら会話も関係値も残っているので続きから話せる。14日を過ぎていればキャラの所有だけが戻る。**Appleが戻せと言っているのは買ったもの、つまりキャラの所有であり、会話履歴は買ったものではない。** これで要件は満たすという判断で、据え置きを解約と同じ14日にそろえた。

# 0. v4.0の前提

## 0-1. 正本ルール

- この仕様書は「何を作るか」を定義する。
- 作業順、PR方針、検証手順は `voice_companion_build_plan.md` で管理する。
- 過去スレの断片や旧メモは正本として扱わない。

## 0-2. ログイン画面なし

VoiceCompanion v1はログイン画面を持たない。

初回起動時、アプリはSupabase Authの匿名セッションを自動作成する。ユーザーに見せる最初の体験は、ログインではなく名前入力とキャラ選択である。

## 0-3. アプリ内ユーザーID

アプリ内ユーザー主キーは `public.users.id` とする。

`auth.users.id` はSupabase Authの認証セッションIDであり、各ユーザー別テーブルの `user_id` として直接使わない。

各ユーザー別テーブルの `user_id` は原則 `public.users(id)` を参照する。

## 0-4. 引き継ぎ

端末変更・再インストール時のアプリ内データ引き継ぎは、Google / Apple / emailログインではなく、引き継ぎコードで行う。

旧端末で引き継ぎコードを発行し、新端末で入力することで、同じ `public.users.id` へ戻す。

引き継ぎコードなしでアプリを削除・再インストールした場合、アプリ内データは原則復元できない。

## 0-5. 本番導線から削除するもの

以下はv1本番導線から削除する。

- Googleログイン
- Appleログイン
- email/passwordログイン
- ログイン画面
- OAuth callback deep link
- SocialLogin依存
- Google client ID前提の本番ログイン
- Apple Sign In capability前提の本番ログイン
- `auth.users.id` をアプリ内ユーザー主キーにする設計
- `RevenueCat app user id = auth.users.id` の設計

email/passwordは過去のデバッグ疎通実績としては残るが、本番導線では使わない。

# A. 体験仕様

## A1. アプリの核

VoiceCompanionの核は「AIと、アニメ声で会話する」こと（文字・音声）である。

恋愛・告白は後から乗った付加要素であり、アプリの核ではない。

優先順位は「会話×アニメ声＝主／恋愛＝従」。

実装で迷ったら、会話・アニメ声・キャラが日常に現れる体験を優先し、恋愛要素は削る/後回しにする判断もあり得る。

VoiceCompanionは、ユーザーが自分から開いて話すだけのAIチャットではなく、AIキャラ側からユーザーの日常に現れるアプリである。

ただし通知専用アプリではない。ユーザー発信の疑似LINE・疑似電話も、関係行動として扱う。

主な入口:

- モーニングコール
- デイリー通知
- 気まぐれ通知
- イベント通知
- 特別イベント疑似着信
- 疑似LINE
- 疑似電話
- ランダム猫 / AI猫

AlarmKitやAndroid full-screen intentは、この体験を成立させる実装手段であり、アプリ価値そのものではない。

## A2. v1 MVPスコープ

v1に入れるもの:

- ログイン画面なしの匿名セッション自動作成

## A5. 関係性・親密度・呼び方

人間キャラは以下を持つ。

- 親密度（共通ベース・友人スコア・恋人スコアの3つ）
- ユーザー側好意度
- 関係状態
- 恋愛イベント許可フラグ

関係状態:

- `friend`
- `close_friend`
- `romance_event_pending`
- `lover`

猫は懐き度と最後に構った時間を持つ。猫は恋愛状態・告白イベントを持たない。

AIが自由に点数を決めない。サーバ固定ルールで増減する。LLMは分類や候補抽出に留め、最終判定はサーバ側が行う。

### A5-1. 3つのスコアと総合点

親密度は3つのスコアを持ち、いずれも上限を設けない。確率計算やAI入力には無制限の生値をそのまま使わず、用途別の補正値・関係段階へ変換して使う。

**総合点 ＝ 共通ベース ＋ 友人スコア ＋ 恋人スコア**

- 共通ベース … 関係の総量。会話した日数の物差し。告白の時間の床。A10-2スケジューラが読む値。関係の種類が変わっても引き継ぐ
- 友人スコア … 友人方向の深まり
- 恋人スコア … 恋愛方向の深まり。告白の下限条件

節目の判定は原則この総合点で行う。3つを別々の閾値で見ると、恋愛志向のユーザーが友人スコアで置いていかれ、呼び方が「苗字さん」のまま告白される不整合が起きる。個別スコアを単独で見るのは、親友の節目と告白の下限条件だけとする。

### A5-2. 加算

日次処理で1日1回、その日の会話を1つのカテゴリへ分類して加算する。分類は長期記憶の要約と同じAI呼び出しに相乗りさせる。何回会話しても点数はその日1回分であり、回数では増えない。

共通ベースは会話が成立した日に一律 +5。会話の中身では変えない。その日に消費したコインの量で2段階の上乗せを付け、19〜36コインで +1.5、37コイン以上で +3 とする。上限を置き、消費量へ無制限に比例させない。境界は無料付与の1日分18コインを1枚でも超えた量と、2日分36コインを1枚でも超えた量に置く。無料付与は繰り越さないため、無料のままでは上乗せに届かない。

中身の点はカテゴリごとに友人スコアと恋人スコアへ配分する。

- 好意・甘え … 友人 +2、恋人 +3
- 相談・打ち明け … 友人 +3、恋人 +2
- 日常・雑談 … 友人 +1、恋人 +1
- 該当なし（挨拶だけ・意味のある内容がない極端に短い会話） … 0

「好意・甘え」と「相談・打ち明け」の総合点は揃える。恋愛志向でも友情志向でも呼び方の節目が同じペースで進むようにするため。どのカテゴリでも配分をゼロにしない。一方の会話ばかりするユーザーの片側スコアが永久に0になることを避ける。

その日の会話量に応じて、中身の点にだけ ×1〜×2.0 の倍率をかける。会話量はその日に消費したコイン量で測り、境界は無料付与の1日分を1枚でも超えた量、すなわち19コインに置く。共通ベースの上乗せと同じ境界である。無料付与は1日18コインで翌日へ繰り越さないため、無料のままでは ×2.0 に届かない。無料の範囲で関係の進むペースを上げられないようにするためである。

倍率を1.5でなく2.0にしたのは、1.5では告白までの日数が共通ベースの上乗せ+2で頭打ちになり、上の段に意味がなくなるためである。告白の3条件のうち恋人スコア300点には共通ベースの上乗せがかからず、倍率だけが効く。したがって上乗せをいくら増やしても恋人スコアの到達日は動かず、そこが最後に残る。2.0にすると+3まで効き、雑談中心の利用者の告白も200日から150日へ縮む。

カテゴリはその日いちばん多くを占めた性質を1つ選ぶ。マイナスが1回でもあった日はマイナスを優先する。一番高いカテゴリを採る方式にはしない。毎日1言だけ好意を伝えれば済むようになるため。

カテゴリ判定を往復数に依存させない。1往復でも中身があれば「相談・打ち明け」として扱う。往復数で判定すると、無料コインで1往復しかできないユーザーが構造的に雑談どまりになり、会話量を点数に反映しないという設計が抜け道から崩れる。

### A5-3. 減点

減点は加点より小さくする。減点は2系統ある。

**疎遠による減衰**

- かかる先は友人スコアと恋人スコア。共通ベースは減らさない
- 最後に会話した日から7日間は猶予。8日目から友人・恋人それぞれ 1日 −0.5
- 下限はそれぞれ到達した最高値の半分。ゼロへは戻さず再開の余地を残す

共通ベースを減らさないのは、共通ベースが「会話した日数」であり続けることで告白の時間の床を日数として保証するためである。

**会話内容によるマイナス**

暴言・突き放し・安全方針に触れる要求を対象とする。そっけない会話・盛り上がらなかった会話は減点対象にしない。

- 1日目は友人・恋人それぞれ −3、連続2日目は −6、連続3日目以降は −12 で頭打ち
- プラスに分類される日が1日でも出たら1日目の幅に戻す
- 友人・恋人スコアは0より下へ行かない
- 共通ベースはその日も +5。暴言の日も会話は成立しているため。ただし総合点は下がる

### A5-4. 節目

節目は5つあり、告白はその一番奥の1つでしかない。告白だけを切り出して設計しない。

1. 苗字さん → 名前さん … 総合点 200
2. 名前さん → 呼び捨て … 総合点 450
3. 親友（`close_friend`） … 共通ベース ＋ 友人スコア が 560
4. あだ名 … 総合点 950
5. 告白 … A10-5 の3条件

名字を登録していないユーザーは「苗字さん」を飛ばす。

親友だけ恋人スコアを使わない。関係の「種類」を決める節目なので、その種類の物差しだけで見る。打ち切り時に恋人スコアの一部が友人スコアへ移ると、この物差しがそのまま上がり、振られたあと友情の側が進む動きが自然に出る。

`close_friend` は画面に表示しない。到達を知らせる通知も置かない。効くのは着信確率とLLM文脈だけである。

一度到達した節目は、点数が下がっても巻き戻さない。閾値割れで戻す方式にすると、節目を超えた直後のユーザーだけが戻る運任せの挙動になるため。代わりに日数で戻す。

- 最後に会話した日から90日ごとに、呼び方を1段階戻す
- 下限は「名前さん」。苗字さんへは戻さない
- `close_friend` と `lover` は戻さない
- 会話を再開すれば次の日次処理で元の呼び方に戻す。点数は足りているので取り直しにしない

`lover` を戻さないのは、告白の結果が点数ではなくユーザーがボタンで答えた事実だからである。

### A5-5. 呼び方

呼び方は関係の到達点として扱う。登録時に必須なのは名前だけ。呼び方の初期指定UIは置かない。呼び方はキャラごとに持ち、関係値で解禁される。

ユーザーが「〇〇と呼んで」と希望しても、関係値/親密度が足りなければキャラが断る。受ける/断る判定はサーバ固定ルール。セリフ生成はLLMでよい。

### A5-6. 恋愛イベント許可フラグ

`romance_event_allowed` はユーザーが設定画面でキャラごとに切り替える。男女両方のキャラがいるため、同性キャラを友達として使いたいユーザーが必要とする。

OFFのキャラでは恋人スコアをそもそも積まない。「好意・甘え」に分類された日も恋人スコア分は入らない。積むが判定に使わない方式は採らない。ONにした瞬間に条件を満たして唐突に告白が来るため。切り替えても得をしない（恋人スコアは0から）ので悪用の余地はない。

### A5-7. 数値の持ち方

A5の数値は、A10-2の`SCHEDULER_CONFIG`と同様にサーバー側の設定として1箇所へ集約し、アプリ更新なしで変更できる形にする。リリース後の調整を前提とする。

## A6. 猫仕様

猫は人間キャラと同じ土俵で疑似LINE・疑似電話・モーニングに乗る。違いは人間語を返さない点。

- 猫は恋愛要素なし
- 猫は親密度ではなく懐き度
- ランダム猫はAIなし・無料
- AI猫は感情/反応分類あり・コイン消費
- 疑似LINEでは鳴き声・しぐさテキスト
- 疑似電話/モーニングでは鳴き声音声
- 鳴き声はTTSではなく音声ファイル
- v1ではなで等のタップUIや本格アニメは持たない

## A7. 疑似LINE

疑似LINEは、ユーザーとキャラの基本接点である。通知を開いた後の入口、通話への導線、イベント導線、通話見出しの履歴表示を兼ねる。

疑似LINE履歴は `chat_messages` に保存する。チャット本文と通話見出しは90日で自動削除する。重要なものはピン留めで残せる。

疑似電話後は、疑似LINEに通話見出しを差し込む。通話本文の逐語ログは疑似LINEには入れない。

文字チャットは、AI返信1回ごとの固定コイン消費を基本とする。チャットの文字数上限があるため、入力・出力トークン数による細かな従量計算は行わない。1返信あたりの消費量は**3コイン**とする（F1で確定）。固定文言・システム都合の文言・エラー文言は消費しない。

## A7-1. 疑似LINEホーム

疑似LINEホームは、LINEのトーク一覧のようなメイン画面であり、アプリを開いた後の中心画面である。

表示するもの:

- 上部: トークメイトAI
- 上部: コイン残高
- 上部: 設定アイコン
- 中央: 8キャラのトーク一覧
- 下部ナビ: トーク / キャラ / コイン / 設定

キャラ一覧は8キャラすべてを表示する。初期設定で選んだキャラを一番上に表示し、未選択キャラは選択済みキャラより弱く見せる。

ホームでは最後のメッセージ本文を表示しない。ホームで本文を見せると、ユーザーがチャットを開かずに満足する可能性があるためである。

代わりに状態だけを表示する。状態表示の例:

- 新着あり
- 会話できます
- 追加できます

選択済みキャラをタップした場合は疑似LINEチャット画面へ遷移する。未選択キャラをタップした場合はキャラ管理 / キャラ追加導線へ遷移する。

## A8. 疑似電話

疑似電話の入口:

1. ユーザー発信の通話
2. モーニングから会話へ進む通話
3. 日常の気まぐれ着信に応答する通話
4. 特別イベント疑似着信に応答する通話

通常通知は直接通話の入口ではない。疑似LINE画面から通話ボタンで疑似電話へ進む。

iOSの日常の気まぐれ着信は通常APNs通知で知らせる。バックグラウンド・終了中・ロック中は
28.5秒のカスタム通知音を鳴らす。配信から30秒以内の通知タップ後は、同じ音源と反復バイブを
アプリ内疑似着信画面で最大30秒続ける。アプリ前面ではOS通知を重ねず直接疑似着信画面を開く。
PushKit / CallKit / AlarmKit / `ringtoneSoundNamed`は使わない。通知中のバイブ回数と継続は
iOSの通知制御に従い、アプリから29秒の反復を保証しない。AlarmKitはユーザーが登録した
モーニング専用であり、気まぐれ着信には流用しない。

Androidのモーニングはfull-screen intentを使う。日常の気まぐれ着信も通話用full-screen intentを
使うが、通知channel、payload、Activity入口、音の責務はモーニングと分離する。アプリ前面では
OS通知を作らず直接アプリ内全画面疑似着信へ切り替える。前面外では通話カテゴリ通知を出し、
未ロック中はheads-up、全画面通知許可済みのロック中は自動全画面とする。通知上の直接応答・拒否は
使わず、heads-up通知のタップまたはロック中のfull-screen intentからアプリ内着信へ進む。

特別イベント疑似着信は、通常通知 → 疑似LINE → 電話していい？ → OK → アプリ内疑似着信画面 → 応答 → 疑似電話、の流れにする。

日常の気まぐれ着信は、着信を許可したユーザーに対して、着信サイレント時間外だけ
キャラから直接かかる。アプリ前面、バックグラウンド、終了中、ロック中を両OSの対象とする。
応答するまでcall、録音、AI接続、課金、疑似LINEの通話見出しを作らない。拒否・無応答でも
これらを作らず、準備済み接続があれば破棄する。拒否・無応答・第一声準備失敗は対象キャラの
疑似LINEへ不在着信履歴を1件だけ残す。配信候補、端末別配信結果、拒否・無応答・準備失敗という
サーバ内部の運用記録は、頻度制御、診断、重複防止のため保存してよい。

通話開始前に確認するもの:

- 匿名セッション確立済み
- `public.users.id` 解決済み
- 対象キャラ
- マイク権限
- コイン残高
- 通話開始元
- 別通話中でないこと

課金単位は**60秒までを10コイン、以後30秒ごとに4コイン**とし、端数は切り上げる（F1で確定）。開始前に1課金単位分＝**10コイン**の残高を確認する。通話全体の前払いは行わない。

発話中からストリーミング文字起こしを進めるが、AIに渡すのは発話終了が確定した後の確定発話テキストだけ。暫定文字起こしはAIへ渡さず保存しない。

保存するのは確定発話テキスト。

Android実機ではWebViewの `getUserMedia()` に依存しない。

ネイティブ `AudioRecord` で 24kHz / mono / PCM16 を取得して `voice-turn` へ送る。

iOS実機でもWebViewの `getUserMedia()` に依存しない。ネイティブ `AVAudioEngine` で取得したマイク音声を 24kHz / mono / PCM16 へ変換して同じ `voice-turn` へ送り、通話usage・ログ・精算はAndroidと同じOS共通イベントとTypeScript層へ接続する。

AIへ送らないもの。

- 無言
- 咳
- 物音
- 短すぎる音
- 意味のないノイズ
- TTS再生音の回り込み

無音判定時間はユーザーに数値を直接出さず5段階で選ばせる。

- かなり速い = 300ms
- 速い = 400ms
- 標準 = 500ms
- ゆっくり = 700ms
- かなりゆっくり = 900ms

AIには、キャラ基本情報、関係情報、ユーザー理解シート、同日短期文脈、直前LINE/通知文脈、現在の通話内履歴、今回の確定ユーザー発話を渡す。全ログを毎回全文で渡さない。

疑似電話中のAI応答はTTSでキャラ音声再生する。応答テキストは通話中に表示しない。通常応答は1〜3文程度。モーニング由来はさらに短め。

固定文言はAI応答ではなくアプリ側の状態文言であり、その再生時間は課金対象にしない。固定文言にTTSを使っても、AI通常回答でなければ課金対象にしない。

通話は1応答ごとの固定消費ではなく、同じ通話内の次の課金対象時間を合算して計算する。

- 各ユーザーターンの経過時間
- AIの通常回答音声が端末で実際に再生された時間

ユーザーターンは、アプリがそのターンの録音を開始してから、そのターンの終了を確定するまでとする。話し始めるまでの時間、実際に話している時間、話の途中で考えている沈黙、言いよどみ、発話終了判定までの時間、何も話さず無音・聞き取り失敗としてターンが終了するまでの時間を含む。

「無音を課金対象にする」とは、ユーザーターン中の沈黙時間をユーザーターンの経過時間に含めるという意味であり、STT、LLM、TTS、通信などの処理待ちを含める意味ではない。

AI側は、通常回答のキャラ音声が端末で実際に再生された時間だけを含める。再生開始前の時間、生成されたが再生されなかった音声は含めない。途中で再生を止めた場合は、実際に再生された部分だけを対象にする。

呼出中、接続前、WebSocket接続待ち、STT処理待ち、LLM回答生成待ち、TTS生成待ち、音声ファイル取得待ち、通信待ち、再接続待ち、アプリ側の処理遅延、固定の聞き返し音声、エラー案内音声、通話前の固定音声、Good morning onlyの固定音声は課金対象時間に含めない。

内部ではターンごとにユーザーターンの経過時間とAI通常回答音声の実再生時間を記録できる構造とする。通話終了時に同じ`call_id`の記録を合算し、1通話分の消費コインをまとめて確定する。通話中にターンごとに即時減算しない。

アプリ強制終了、異常切断、通信断などでも、保存済みの計測記録から未精算通話を確認・精算できる構造を要件とする。回収と再試行の方法は次のとおりとする。**推測で課金しない**ことを共通の原則とし、記録から確定できる通話だけを精算する。

**端末側の再送。** 計測は所有者付きの永続outboxへ積み、通信に失敗しても保持して次回起動時に再送する。精算RPCを送るのは、全ターンの計測が確定し、未精算として保存できた後だけとする。起動時にはoutboxを本人所有callのDB状態と照合し、精算済み・不存在・所有不整合はローカルから除き、通信失敗は保持する。

**サーバ側の日次回収。** 端末から終了が届かなかった通話を、1日1回まとめて片付ける。**最終活動から24時間**経過したものを対象とし、**毎日03:30（日本時間）**、**1回100件**まで、古い順に処理する。24時間は通常の通話時間の上限とは別の、無活動の猶予である。

- 計測が1件も無い空の通話（`active`・0ms・ログ0件）は、0コインで打ち切る。台帳は作らない
- 全ターンの計測が確定して保存済みで、期待件数とも矛盾しない通話は、保存済みのログから合計時間を復元して精算する
- 本文だけの通話、計測が未確定の通話、件数が合わない通話、最終活動から24時間以内の通話は**推測せず翌日へ回す**

**二重課金の防止。** 端末からの精算とサーバの日次回収は同じ精算処理を通す。通話1件ごとのidempotency key、通話行と残高行のロック、消費IDの記録により、同じ通話を何度実行しても減算・台帳とも1回だけとする。精算後に課金対象時間を書き換えることはできない。

通話終了時に、少なくとも今回消費したコイン数を確認できる構造にする。課金対象時間の内訳や秒数を利用者へ表示するかはF5で決める。

### 残高が尽きる前の予告

通話中に残高が尽きて不意に切られることのないよう、事前に1回だけ予告する。

**話せる残り時間が20秒を切ったら予告する。** 判定は残り枚数ではなく残り時間で行う。
通話中は残高が減らない（精算は通話終了時に1回）ので残り枚数と残り時間は同じものだが、
残高10〜13コインの利用者は最初の60秒ぶん10コインを払った時点で残り枚数が4を通らず、
枚数で判定すると予告が一度も出ないためである。

**予告はキャラの声ではなく、事務的なアプリの音声で流す。** 全キャラ共通の同じ文言とし、
AIの返事が終わった直後に鳴らす。利用者の発話には割り込まない。キャラに残高の話をさせず、
アプリからのお知らせとして分けるためである。全キャラ共通の1本で足りるため、キャラごとの
文言も声も用意しない。

この音声はLLMもキャラの声モデルも使わないので課金対象時間に含めない。**鳴らすのは端末に
入っている読み上げ音声（iOS `AVSpeechSynthesizer` / Android `TextToSpeech`）である。**
音声ファイルは同梱しない。読み上げ機能や日本語の声が無い端末では鳴らないので、その場合は
待たせずに次へ進め、画面の表示だけを出す。キャラの声モデルは端末へダウンロードして使うため、
1文のために事務声のモデルを増やさない。

通話中は近接センサーで画面が消えていることが多く、画面表示だけでは届かない。よって音声を
主とし、画面を見ている利用者のために画面表示も残す。

予告の文言は音声・画面とも次の1文で共通とする。

> **残りコインが少なくなっています。**

**秒数を言わない。** 残り20秒は課金される時間であって時計の20秒ではなく、考えている沈黙や
返事を待つ時間は課金されないため、実時間ではもっと長く話せる。「あと20秒で終了します」は
嘘になる。同じ理由で画面表示にも残り秒数を出さない。

**「なくなる」ではなく「少なくなっています」とする。** 話せる時間は課金単位の切りのよい
ところで終わるため、残高が0にならず端数が残ることがある（B10参照）。

**購入の案内はこの文言へ入れない。** 通話中に購入する導線を設けないためである。

予告の音声は、AIの返事が終わってから鳴らす。返事の途中で残り20秒を切った場合は、その返事が
終わるまで待つ。

**聞き取れなかったときの固定文言のあとにも鳴らす。回数は問わず、1回目・2回目でも鳴らす。**
固定文言はAIの返事ではないが、そのあと会話が戻る保証が無い。戻るのを待つと、聞き取り失敗が
続いたまま終わった通話で予告が遅れる。固定文言が鳴り終わってから予告を鳴らし、そのあと
録音へ戻る。利用者の発話には割り込まない点は変わらない。予告そのものは通話で1回だけである。

### 残高が尽きたときに切るタイミング

**話せる残り時間が0になった、その瞬間に切る。** 言葉の途中でも待たない。

課金される時間は、利用者が話しているターンと、キャラの声が鳴っている時間の2つだけである
（処理待ちは数えない。A8-1参照）。つまり0になる瞬間は必ずそのどちらかであり、**必ず途中で
切れる。** それを承知のうえでこの形にする。

待つ形（鳴っている返事が終わるまで、あるいはそのターンが終わるまで待つ）を採らないのは、
待ったぶんが払われていない時間になり、超過を無料にするか未精算として持ち越すかという
別の決めごとが要るからである。0で切れば、払ったぶんだけ話したことになり、精算も一致する。

**ただし実際には、切ると決めてから止まるまでのぶんだけ必ず超える。** その扱いは次項に定める。

切れる前に予告の音声を1回鳴らしている（本節の予告を参照）。

残高が足りなくなって通話が終わったあとの画面と導線はB10に定める。

### 通話中に他のアプリへ移ったとき

**通話を終了する。** 自分で終了を押したときと同じ終わり方にし、話したぶんのコインを引く。

通話を残したままにすると接続が切れ、「通信に失敗しました」と出て「もう一度試す」が
押せる状態になる。時間は課金されているのに何が起きたのか分からない。切ってしまえば
話した分だけ引かれて終わる。

通知が出ただけでは切れない。タップして他のアプリが開いたときに切れる。

トークのタイムラインへ、キャラの発言ではないお知らせを1枚置く。

> 他のアプリを開いたため通話を終了しました

**コインは引かれているので、何も出さないと利用者から見て理由が分からない。** コイン切れの
文言は使わない。足りているのに足りなくなったと書くことになるためである（12枚で始めた通話が
60秒で終われば10枚引かれ、2枚残る）。購入導線も付けない。

**通話の終わり方のお知らせは、1キャラにつき1枚だけ残す。種類は問わない。** コイン切れの
ぶんとこのぶんが並ぶと、どちらが今の話か分からなくなる。

残高が足りなくなって通話が終わったあとの画面と導線はB10に定める。

### 使い切って終わった通話の精算

**持っている枚数で払える上限を超えた請求はしない。** 12枚持っている利用者が60秒の上限を
使い切ったら、10枚だけ引いて端数の2枚は残す。残高を0にはしない。

上限ちょうどで切っても、記録される時間は止まるまでのぶんだけ数十ms超える。料金は60秒を
1msでも超えると次の単位に入る（10枚→14枚）。上限は「その残高で払える最大」として決めて
いるので、**超えた瞬間の料金は常に払える額より1単位多い。** そのまま請求すると必ず払えず、
1枚も引けないまま終わる。つまり残高を使い切って終わった通話が毎回タダになる。

払える上限で頭打ちにするのは、この形なら残高がいくつでも同じ結果になるためである。
「使い切ったら0にする」とはしない。精算は終話の後に走るので、ちょうどその時に日付が
変わって毎日の無料コインが入っていることがあり、入ったばかりのぶんまで消える。

**記録は書き換えない。** 実測の課金時間はそのまま残し、実際に引いた枚数を別に残す。両方を
見れば、払える上限で頭打ちにしたことが後から分かる。

**話せる上限は端末側でも締め切る。** 画面側（アプリのJavaScript）のタイマーだけに任せない。
通話中に他のアプリへ移ると端末はそのタイマーを間引くため、上限を大きく超えて話せてしまう。
超えたぶんは上の決めごとにより請求されないので、そのままタダになる。両OSとも、通話開始時に
渡した上限を端末側が持ち、達したら端末側で通話を止める。

## A8-2. アプリ内疑似着信の接続と音

アプリ内疑似着信では、応答から会話開始までの待ち時間を最小にする。

- 着信画面の表示中に、通話接続の事前準備(WebSocket接続のstandby確立)を裏で進めてよい。ただし録音・課金・call作成は応答するまで開始しない。
- 拒否した場合、事前準備した接続は破棄し、DBに痕跡を残さない。
- 着信中は着信音を鳴らす。応答または拒否で即座に停止する。
- ユーザー発信の疑似電話では、発信開始から接続確立までコール音(呼び出し音)を鳴らす。
- 接続確立後、キャラの第一声を再生してから会話を開始する。通常のユーザー発信と特別イベント疑似着信では、キャラごとの固定第一声(「もしもし」等)を使う。
- 第一声は毎回のTTS生成ではなく、キャラごとの固定音声とする。固定音声のため課金対象外(AI通常回答音声に含めない)。
- 固定第一声の音声素材の作成・保存は fixed_voice_assets 整備工程で行う。それまでは第一声なしで、接続と音の仕組みのみ先行実装する。
- ただしモーニングの`応答`はA9を優先し、固定第一声を使わない。現在日時、関係性、記憶を踏まえてAIが毎回第一声を生成する。
- 着信音・コール音は生成音声(TTS)を使わず、固定音源または合成音とする。
- 着信音・バイブは端末のマナーモード設定に従う。通常時は着信音+バイブ、マナー(バイブ)時はバイブのみ、サイレント時は無音とする。
- 着信音・コール音の本番音源はF6の音声素材工程で差し替える。
- キャラの発話が終わって録音を再開する前に、短い録音準備音(ピッ音)を鳴らす。この音は課金対象外とし、生成音声(TTS)を使わず合成音とする。
- 録音準備音は、鳴らす／鳴らさないをユーザーが設定画面で選べるようにする。Android・iOSで同じ動きとする。会話が機械的に感じられることを避けたい利用者が消せるようにするため。既定値はF1で決める。

## A8-3. 音声合成(TTS)方式

疑似電話・モーニング等でのAI通常回答のキャラ音声再生は、オンデバイスTTSで行う。

**方式:**

- 端末上のONNX Runtime + Style-Bert-VITS2系AIVMX(各キャラの声モデル)によるオンデバイスTTSだけを採用する。対象はv1の6キャラ全員(H1参照)。桜音1モデルに絞る前提にはしない。
- クラウドTTSは使用せず、クラウドTTSフォールバックも設けない。クラウドTTSの生成・受信・再生・切替分岐を正式実装へ含めない。
- 方式・量子化・配信が実際に成立するかの検証・テストには、桜音(AIVMX)を基準モデルとして用いる。下記の実測基準値も桜音での計測値。
- 理由: TTS従量課金では採算が成立しない。オンデバイス化により、通話・通知の音声再生でTTS変動費が発生しない構造にする。
- `poc/on-device-tts` ブランチでの実験フェーズは終了し、採用を決定済み(2026-07-18)。実験記録は `poc/notes.md` に保持する。

**モデル構成:**

- TTS本体(AIVMX): 動的INT8量子化(MatMul対象・per-channel QInt8)。実機で音質劣化なしを確認済み。主目的はモデルサイズ縮小。
- DeBERTa BERT: 動的INT8量子化。韻律品質維持のため有効のまま使う。BERTスキップ(無効化)は採用しない。
- このうちDeBERTa BERTは全キャラ共通(共有)コンポーネントであり、キャラ別に異なるのはAIVMX(声モデル)・voice-config・ライセンスのみ。
- 量子化・検証はローカルでは行わず、staging AAB workflowのCI内でのみ実行する。

**再生方式:**

- 文末(。!?)単位でストリーミング合成・逐次再生する。1文目の再生開始を早め、体感遅延を短縮する。
- 読点(、)による細分割は、区切りが不自然になるため採用しない。

**声モデルの配信:**

- 声モデルは初期アプリに同梱しない。初回キャラ選択と追加キャラ選択のそれぞれで、選択を確定した時点にCloudflare R2から端末へダウンロードする(egress無料のため)。Android・iOSで同じ動きとする。
- 通話開始を未取得モデルの初回ダウンロード起点にはしない。キャラ選択後、通話を始める前にそのキャラのモデル取得・検証・導入を完了できる導線とする。取得中・失敗時の表示と再試行はキャラ選択導線で扱う。
- **取得中もそのキャラのトークは開けて、メッセージも送れる。** 100MB規模で25分ほどかかることがあり、その間そのキャラで何もできないのは待たせすぎである。テキストのトークは声モデルを使わないため止める理由がない。
- **取得中は通話だけを止める。** ボタンは消さずに押せなくし、取得中であることを文言で出す。押せると、声が無いまま何分も無音で待たせることになる。取得が終わったら、画面を止めない短い知らせで伝える。モーダルで割り込まない。
- 配信は共通BERT bundle(共有DeBERTa BERT＋共通ライセンス。端末へ1回だけDLして保存・再利用)と、キャラ別bundle(AIVMX＋voice-config＋モデルライセンス。キャラごとにDL・保存)に分割する。桜音→別キャラ→桜音のようにキャラを切り替えても、共通BERTと既取得済みキャラモデルは再ダウンロードしない。片方のDL/検証/更新の失敗が既存の正常インストールを壊さない。
- 導入済みbundleはアプリの永続領域へ保存し、通常のアプリ再起動・端末再起動では再ダウンロードしない。bundleの版更新、未取得キャラの選択、アプリ削除後の再インストール等、導入済みbundleを再利用できない場合だけ取得する。
- ライセンス表記文書は声モデルのダウンロード時に同梱・保存する(H1参照)。

**実測基準値(参考):**

- 計測端末: POCO X6 Pro(Dimensity 8300-Ultra)、CPU実行プロバイダ、4スレッド。
- 1文目の再生開始まで約0.9〜1.0秒、RTF約0.7、セッション初期化 約5.5秒(常駐・初回のみ)。
- この端末水準(iPhone 12相当)を、当面の仮の推奨基準端末とする。低速端末対策はF6で決める。

**本実装の要件:**

- 本格実装では、通話フリーズ(応答が返らず固まる)の切り分けのため、STT / LLM / TTS / 再生の各区間ごとにどこで停滞したかを記録するログを含める。

**正式なAndroid通話構成:**

- `AndroidTtfaTestPlugin`は検証用の暫定実装であり、正式実装として残さない。新しい正式Android通話実装へ段階的に置き換え、staging切替と実機確認を終えた後に旧Pluginを丸ごと削除する。
- 新実装は最初から、通話ライフサイクルと状態遷移、WebSocket接続・standby昇格・再接続、録音・VAD・STT送信、オンデバイスTTSのモデル管理・合成・再生、課金usage・終了確定、診断の責務に分割する。
- 正式Android通話実装のTTS経路はオンデバイスTTS専用とする。旧Pluginに存在するクラウドTTSの生成・受信・再生・切替分岐は移植せず、移行完了時に旧Pluginとともに削除する。
- 責務の境界を越えても、モデルsession、AudioTrack、合成・再生executorをturnごとまたは文ごとに不要に再作成しない。通話中に再利用できる資源はライフサイクルを明示して再利用する。
- クラス分割を理由に余計なJSONへの変換・再変換、PCMバッファのコピー、スレッド切替を増やさない。PCMは合成から再生まで不要な複製を避け、既存のproducer / playback consumerの順序保証を維持する。
- 初回音声開始と文間遅延を計測可能にし、機能移行後に実測値を基準として改善する。性能改善のために課金、usage、終了確定、接続状態の正しさを崩さない。

## A9. モーニング

モーニングは、キャラが日常に現れる主要導線。単なるアラームではなく、起床後に疑似電話へ進める入口である。

モーニングはスマホ標準アラームの代替として使えることを前提にする。アプリを閉じている、画面が消えている、
端末がロックされている、または通信できない場合でも、端末へ登録済みのアラームは鳴動できなければならない。
AI通話だけは通信を必要とする。

設定画面は通常のスマホのアラーム一覧と同じ構成にする。

- 複数のアラームを登録できる
- 各アラームに時刻、鳴らす曜日、キャラ、ラベルを設定できる
- 曜日指定の繰り返しと、一回だけの指定日時を扱う
- 一覧のスイッチで個別にON/OFFでき、編集・削除できる
- スヌーズ間隔は1〜60分を1分刻みで選択し、初期値は5分とする
- スヌーズ回数は1回、3回、5回、回数制限なしから選択し、初期値は3回とする
- バイブのON/OFFをアラームごとに選べる
- 音とバイブの両方が無効になる設定は警告し、気付けないアラームを作らない

モーニングの鳴動画面は疑似電話として表現する。アプリ内の操作名と処理は次のとおり。

- `応答`: 鳴動を止め、対象キャラとのAI疑似電話を開始する。ユーザーの発話を待たず、現在日時、関係性、記憶を踏まえてAIが毎回生成した短い第一声をキャラから話す。通話可能なコインがある場合はユーザーデータ全体の読込より先に第一声の文章を先行生成し、応答操作で進行中の準備を破棄しない。通話開始準備と並行しても未完了なら最大0.5秒だけ完成を待ち、それでも未完了または失敗なら応答後に生成する。応答時には最新残高を再確認し、拒否・スヌーズ・未応答では通話履歴とコイン消費を発生させない。固定WAVは使わない。第一声が終わるまで録音せず、終わった後は同じ通話内で通常会話へ進む。AI第一声の実再生時間を含め、通常の通話課金規則を適用する
- `メッセージを再生`: 鳴動を止め、通常と同じ通話画面を表示した直後に近接監視を開始し、1.0秒待ってから、事前に用意した対象キャラの固定モーニング音声だけを再生する。再生準備へ移っても近接監視を維持し、受話口へ近づけた間は画面を消す。待機中に通話を終了した場合は再生しない。再生後も通話画面を維持し、ユーザーの終了操作で閉じる。自動ループと再再生ボタンは設けない。マイクと会話AIは使わず、コインを消費しない
- `拒否`: 鳴動を止め、その日のモーニングを終了する。通話や固定音声は開始しない
- `あとで（○分）`: 鳴動を止め、設定された間隔後に再度鳴らす。設定回数へ達した場合は選べない

内部名`good_morning_only`は互換性のため使用してよいが、画面には「おはようだけ」と表示せず
「メッセージを再生」と表示する。

現在の固定WAVは機能検証用の仮素材である。後続のデザイン・素材工程で、現在より長く、
朝の呼びかけとして内容のある正式文言へ3種類とも差し替える。

iOS 26以上ではAlarmKit導線を使う。CallKit / VoIP pushは使わない。カスタムAlarmKit音やアプリ内Web Audioループ音はv1対象外。

AlarmKitの最初のシステム画面は、停止と、アプリを開くカスタム操作の2つとする。停止はそのまま終了する。
アプリを開くと、AlarmKitの音を鳴らしたまま対象キャラの全画面疑似着信を表示し、上記4操作を出す。
各アプリ内操作はAlarmKitを内部で止めてから後続処理へ進み、別の停止ボタンを要求しない。

Androidはfull-screen intent notificationを使い、同時にOSが許す場合は専用Activityの直接起動も試す。
音はForeground Serviceで鳴らし、全画面表示と分離する。

Androidは最初から対象キャラの全画面疑似着信を表示し、上記4操作を出す。Android 14以降では、
全画面表示の許可をアラーム有効化の必須条件とする。未許可の場合は端末の許可画面を開き、許可後の
再保存を求める。許可が無い状態をアラーム設定完了として扱わない。
全画面疑似着信は通常アプリ画面とは別の専用タスクで開く。専用Activityが既に存在していても、
新しいアラームのIntentを必ず取り込み、以前表示していた設定画面等を着信画面として再利用しない。
継続通知の`応答`は対象アラームの応答としてAI通話を直接開始し、通知本文のタップは全画面疑似着信を開く。

OSまたはメーカー制限によりfull-screen intentも直接起動も拒否された場合は、音を鳴らしたまま
継続通知を出す。通知には`応答`と`停止`を表示し、`応答`または通知本体から同じ疑似着信Activityへ入れる。

応答後はMainActivityへ飛ばさない。

ロック解除を前提にした通常アプリ起動ではなく、ロック画面上の専用Activity内でAI通話接続状態へ進める。

AndroidはConnectionService / Telecomを使わない。

モーニングはアラーム系導線として、full-screen intent + Foreground Service + アプリ内疑似通話Activityで構成する。

`応答`と`メッセージを再生`のどちらも、終了後は疑似LINEへ通常と同じ「通話」見出しを残す。
表示上の履歴種別や文言は分けない。

## A8-4. Good morning only

Good morning only は画面上では「メッセージを再生」と表示する。事前に用意した固定音声のみで消費なし。

v1ではキャラごとに3種類の固定モーニング音声を用意する。前回再生した音声を端末内に記録し、
候補が複数ある場合は直前と同じ音声を避けて選ぶ。関係性ごとの増加はv1に含めない。

固定音声は初回・追加のキャラ選択時に、そのキャラの会話用TTSモデルと一緒に端末へ保存する。
モーニング設定・同期時は保存済み音声を確認し、不足または更新分だけを取得する。鳴動時の
「メッセージを再生」は保存済みの音声だけをローカル再生し、LLM、会話用WebSocket、
マイク、コイン消費を使わない。通常と同じ通話画面と「通話」見出しを残すためのcall記録だけは作成する。
音声が未保存の場合は会話AIや端末標準TTSへ
置き換えず、準備中として明示する。会話用TTSモデルが配信されていないキャラは、
選択後に無音となるため選択可能に表示しない。

`応答`で疑似電話へ進んだ後は、AIが生成した第一声を含む通常回答音声の実再生時間と、
その後のユーザーターンの経過時間を合算する通常の通話課金ルールを適用する。

## A9-1. 会話からのモーニング登録

設定画面に加え、キャラとのチャットまたは通話でモーニング登録を依頼できる。

- 「明日7時に起こして」は一回だけの候補にする
- 「毎週月曜から金曜の7時に起こして」は曜日指定の繰り返し候補にする
- 会話AIはアラームを直接登録しない
- 日付、曜日、時刻、繰り返し、キャラを明示した確認を疑似LINEへ出す
- ユーザーが「設定する」を選んだ場合だけ端末とDBへ登録する
- 曖昧な日時は登録候補にせず、キャラが聞き返す
- 通話中の依頼では、キャラが「通話後に確認を送るので、そこで設定して」と音声で伝える
- 通話終了後、同じ確認を疑似LINEへ出す。未確認、拒否、期限切れの候補は鳴らさない
- キャラから起こそうかと持ちかける段を置く。直前のユーザー発言が起きる時刻の話ではあるが、登録の依頼でも提案への同意でもないときは、確認を出さず、その時刻に起こそうかと口で一言だけ聞く。頼まれる前に確認を出さない
- 確認は1キャラにつき1枚までとする。押されないまま会話が続いても積み増さない
- 「設定する」「いらない」のどちらを押したかをトークへ記録する。記録はカードの操作と同じトランザクションで残す。畳んだ候補は記録しない
- 見送られた件をキャラから蒸し返さない。改めて頼まれたときだけ扱う

# A9. 通知

## A10. 通知

v1で扱う通知:

- モーニングコール
- デイリー生成通知
- 気まぐれ通知
- イベント通知

モーニングは通常通知とは別枠。デイリー通知とキャラ側からの着信は、A10-2の共通スケジューラが
一つの枠として割り当てる。デイリー枠は1日1回で、その中身は通知または着信のどちらかになる。
気まぐれは通知と着信に分けず、デイリー枠とは別の一つの枠として扱う。
デイリー枠を毎日1回割り当てる原則は、休眠が続く場合と、利用者が設定で連絡の量を少なめにした
場合に例外を持つ（A10-2・B4）。

通知タップ後の疑似LINE画面には、キャラからの入口メッセージを置く。通常通知では
入口メッセージを唯一の本文とし、通知用の別文面を生成しない。

- 入口メッセージは通知生成時に事前生成して保存する
- デイリー通知は通話開始前のテキストメッセージとし、「もしもし」「聞こえてる？」「電話」「通話」など既に音声通話中であるような本文・話題は候補に保存しない
- ロック画面へ出して安全な入口メッセージは、同じ全文を通知本文にも使う
- 「トーク内容を表示しない」がON、または安全検査に通らない場合だけ、通知本文を「{キャラ名}からメッセージが届いています」へ置き換える
- アプリ前面で同じキャラのトークを表示中は通知UIを出さず、入口メッセージだけを一度反映する
- 別キャラのトーク、ホーム、設定などを表示中は現在画面へ内容を重ねず、OS通知を出す
- アプリがバックグラウンド、画面ロック中、終了中なら、最後に開いていた画面に関係なくOS通知を出す
- 入口メッセージと通知結果の保存先は `notification_candidates`
- 実配信が受理された時点で `notification_logs` を作り、`candidate_id`で生成候補へつなげる。未配信候補のログは作らない
- モーニングは入口メッセージの対象外

通常メッセージ通知と、キャラ側から自発的に始める疑似着信は独立してON/OFFできる。
通知ON・自発的着信OFFを許容する。自発的着信OFFはOS通知許可や通常メッセージ通知を
無効化しない。ユーザーが明示登録したモーニングは各アラームのON/OFFを正とし、
自発的着信OFFには連動させない。

通常メッセージ通知のサイレント開始・終了と、自発的な疑似着信のサイレント開始・終了は
別々に設定できる。通知だけ受けて着信を止める時間帯、またはその逆を許容する。
登録済みのモーニングは、どちらのサイレント時間にも連動させない。

## A9-2. デイリー / 気まぐれ / lover通知

通知が送られる条件:

- 通知全体ON
- そのキャラの個別通知ON
- 配信直前の最新残高が3コイン以上
- サイレント時間帯外
- 枠の割り当てあり
- 有効な端末通知トークンがある

製品上は1ユーザーにつき有効端末を1台だけとする。通知送信時は `device_installations` の有効端末1台へ送る。引き継ぎ完了時に新端末を有効化し、旧端末のPush token、着信、通知、モーニングを無効化する。同一ユーザーの複数端末同時利用と端末間の先着応答はv1対象外とする。

デイリー通知のキャラ枠:

- `lover`が1人以上いる場合は、通知ONのlover全員を毎日の対象にする
- `lover`がいる場合も、それとは別に、通知ONの非loverから関係値重み付きで1人を日替わりで追加する
- `lover`がいない場合は、通知ONのAIキャラから関係値重み付きで1人を日替わり選択する
- 各対象の枠は1日1回で、その中身は通知または着信のどちらかになる。振分はA10-2による
- 選択はユーザー・現地日付・キャラIDから再現可能にし、同日再試行で対象が変わらない
- 関係値重みの正式数値はF3で決定し、それまでは交換可能な暫定式を使う
- 割当と配信は分離し、配信直前にも設定、quiet hours、端末状態を再確認する

## A10-1. 日常の気まぐれ着信

日常の気まぐれ着信は、イベント・告白とは無関係な、キャラからの日常的な直接着信である。

- `settings.incoming_call_enabled = true` の場合だけ候補にできる
- `incoming_call_quiet_hours_start/end` の時間帯には配信しない
- ユーザーが登録したモーニングの前後や、通常通知・別の着信と近接させない
- 日・週単位の上限を持ち、拒否・無応答を頻度調整へ使える構造にする
- 通知と着信の候補時刻、頻度、対象キャラは一つの共通スケジューラで決める。内容はA10-2とする
- 最初の運用では通知だけを実配信し、着信候補を記録だけするdry-runを可能にする
- 残高が10コイン未満なら着信候補を作らない。予定後に残高が減る場合に備え、候補処理時とPush送信直前にも最新残高を再確認し、10コイン未満なら送らない。通常メッセージ候補への振替もしない。応答時にも最新残高を再確認する
- 候補作成時に日時・関係性・記憶を使った短い第一声テキストを生成し、成功した候補だけ配信する
- Androidはアプリ前面ではhigh-priority FCM受信後に第一声PCMを準備し、完了時にアプリ内全画面疑似着信・着信音・バイブ・有効な応答ボタンを同時に開始する。準備中は受信前の画面を維持する
- Androidはアプリ前面外で30秒の通話カテゴリ通知へfull-screen intentを付ける。端末ロック中かつ全画面通知許可済みなら自動で全画面疑似着信を表示し、未ロックでホーム画面または他アプリを表示中はheads-up着信通知を表示して、タップ後に全画面疑似着信へ進む
- Android 14以降では、新規初期設定、既存ユーザーの着信設定有効時の初回起動、着信設定ON時に、通常通知許可の後で`全画面通知を許可`設定を開き、アプリ復帰後に許可状態を再確認する。全画面通知が未許可なら着信設定完了扱いにせず、実着信時はheads-up通知へ縮退する
- iOSのバックグラウンド・終了中・ロック中は、同梱した28.5秒WAVを指定した通常APNs alertを受ける
- 前面外の通知表示はタイトル`{キャラ名}から着信`、本文`着信中`とする。内容非表示設定時はキャラ名を出さず、タイトル`着信`とする
- 自動全画面にならない状態では、配信開始から30秒以内の通知タップで対象通知を消し、着信音と反復バイブを伴うアプリ内全画面疑似着信へ進む
- iOSの前面受信はOS通知を重ねず、直接アプリ内全画面疑似着信へ進む
- iOSの通知中のバイブはOS制御であり、アプリが29秒の反復を保証する要件にはしない
- 通知を開いた時点から全画面着信の30秒を開始する。全画面中にアプリを閉じる、バックグラウンドへ戻す、拒否する、30秒無操作のいずれでも着信を終了する
- 通知を配信から30秒無視した場合と全画面着信を終了した場合は、対象キャラのトークへ`{キャラ名}からの不在着信`を時刻付きで1件だけ残す
- 期限後の通知タップは全画面着信やAI通話を開始せず、対象キャラのトークを不在着信位置で開き、配信済み通知を削除する
- Androidのアプリ前面受信だけは、保存済み第一声のPCM準備完了まで受信前の画面を維持し、準備完了時に全画面着信・着信音・バイブ・有効な応答ボタンを同時に開始する。前面外とiOSは従来どおり全画面着信と着信音を直ちに開始し、同じ全画面内でPCMを準備する。別のローディング画面は設けない
- 第一声の準備中は拒否を常に操作可能にし、応答ボタンだけを無効化してスピナーと`準備中…`を表示する。準備完了時に`応答`へ切り替える。準備前に押した応答を予約して、完了後に自動応答する挙動は採用しない
- Androidは応答後に1.0秒の受話猶予を置いてから第一声の通話接続を開始する。第一声終了後は通常回答と同じ録音準備音（ピッ音）を鳴らし、再生完了・準備音完了・次turn standby readyの到着順にかかわらず必ず録音可能な次ターンへ進む。第一声の実再生時間だけ通常課金規則を適用する。録音準備音のON/OFF設定は後工程とする
- 第一声テキスト生成失敗時は通知を送らない。オンデバイスTTS準備は一度再試行し、それでも失敗した場合は応答、call作成、録音、課金を行わず不在着信にする
- iOSの気まぐれ着信にPushKit、CallKit、AlarmKit、`ringtoneSoundNamed`を使わない
- Androidのモーニング用Alarm Service、iOSのAlarmKitへ気まぐれ着信を混在させない
- 応答後は両OSとも`spontaneous`を発信元として既存のOS共通通話開始処理へ合流する
- candidate IDと有効端末1台を照合し、期限切れ、重複配信、別ユーザーの応答を拒否する

## A10-2. 通知・着信の共通スケジューラ

デイリー枠と気まぐれ枠について、対象キャラ、通知か着信かの振分、配信時刻を一つのスケジューラで
決める。通知だけ、着信だけを別々に割り当てる形にはしない。

**枠の構造:**

- デイリー枠は1日1回とし、中身は通知または着信のどちらかにする
- 気まぐれ枠はデイリー枠とは別に持ち、中身は同じく通知または着信のどちらかにする
- 気まぐれは日・週の上限を保険として持つが、上限まで使い切る形にはせず毎日抽選で発生させる。
  上限を毎回使う運用は回数が規則的になり、人からの連絡として不自然になるため採用しない
- 1日に成立する着信は最大1回とする。デイリー枠と気まぐれ枠のどちらが先でも、先に着信が入った
  側を着信とし、もう一方はその日は通知にする

**対象キャラ:**

- デイリー枠の対象はA9-2による
- 気まぐれ枠の相手は、通知ONの全キャラから関係の深さの重みで1人選ぶ
- 同じ日にデイリー枠で接触したキャラは気まぐれの重みを下げるが、除外はしない。loverは毎日
  デイリー枠の対象になるため、除外するとloverから気まぐれが永久に来なくなる
- この結果、loverとは1日2回やりとりする日が出る。これは許容する

**通知か着信かの振分:**

- 関係が深いほど着信になる割合を上げる
- 着信設定がOFFなら、その枠は最初から通知にする
- 着信サイレント時間帯は、最初から時刻の候補に入れない。生成後に弾く形にはしない
- 残高がスケジューラで決める基準未満なら通知にする
- 購入・サブスクの`coin_lots`を持たない無料のみのユーザーは、着信になる割合を下げる。ゼロには
  しない。着信を一度も体験しないまま離脱すると、課金の動機そのものが生まれないため
- 休眠中は着信にせず通知だけにする
- 予定時の振分後も配信直前に最新残高を確認する。通常メッセージは3コイン未満、着信は10コイン未満ならその枠を送らず終了し、相互に振り替えない

**配信時刻:**

- 固定時刻には配信しない。起きている時間帯の中から時刻を抽選して散らす
- 着信サイレント時間帯を設定していないユーザーにも既定の夜間帯を適用し、夜間には配信しない。
  未設定を理由に深夜へ配信しない
- ユーザーが自分から通話またはチャットで接触したキャラは、そのキャラからの配信時刻を後ろへ
  ずらす。ずらした先が配信可能な時間帯に収まらない場合は、その日は配信しない
- 近接回避の間隔は、同じキャラからの連絡と別キャラからの連絡で別々に持つ。同じキャラは長く、
  別キャラは短くてよい
- 同じキャラで間隔を確保できない場合は、気まぐれ枠を送らない。デイリー枠を優先する
- ユーザーが登録したモーニングの前後には配信しない

**休眠時の減衰:**

- 最終利用からの日数に応じてデイリー枠の頻度を落とす。完全には止めない。呼び戻しの機会を残す
- アプリを開いた時点で通常の頻度へ戻す
- 休眠中は着信にせず通知だけにする。無料コインが毎日回復するため、残高では休眠ユーザーへの
  着信を止められない

**利用者による頻度設定:**

- 設定画面で連絡の量を3段階から選べるようにする
- この設定が動かすのは連絡の量だけとし、着信になるか通知になるかは変えない。着信が不要な
  利用者は着信設定をOFFにできるため
- 少なめではデイリー枠も毎日ではなくなり、気まぐれも減る。気まぐれをゼロにはしない

**F3 v2正式値:**

- 少なめ: デイリー50%＋気まぐれ基準7%
- ふつう: デイリー100%＋気まぐれ基準15%（既定値）
- 多め: デイリー100%＋気まぐれ基準45%
- A10-2が読む`intimacy_score`はA5の共通ベースの生値である。共通ベースは会話が成立した日に
  +5ずつ伸びて告白の床600を超えても止まらないため、本節の各式へ渡す前に**6で割って0〜100へ
  丸める**。告白の床600がちょうど補正値100に対応する。以降の「親密度」は変換後の0〜100を指す
- 気まぐれの実発生率は、先に関係値重みで相手を1人抽選し、そのキャラの基準率へ
  `0.75 + 親密度×0.005`（倍率0.75〜1.25）を掛ける。
  親密度0／50／100なら、ふつうの気まぐれ率は11.25%／15%／18.75%となる。所有キャラが
  1人だけでもこの補正は有効とし、関係が深くなるほど少しずつ発生率が上がる
- 気まぐれ上限は1日1回・週3回。着信は全枠を合わせて1日最大1回
- 同一キャラは6時間、別キャラは90分、利用者からの連絡後は3時間、モーニング前後は90分空ける
- 配信可能時間は現地8:00〜21:59。7日休眠でデイリー発生率を45%、30日休眠で20%へ減らし、休眠中は通知だけにする
- 着信最低残高は3。無料のみの利用者は関係値から求めた着信率へ45%を掛ける
- キャラ選択の関係値重みは`1 + 親密度÷20`。整数段階へ
  切り捨てず、1点ごとに連続して変える。複数キャラでは関係が深いキャラほど当選しやすく、
  同日デイリー相手の気まぐれ重みは35%へ下げる
- 着信率は基礎8%にlover 18%／close_friend 10%、affinity_level 1段階ごと5.5%、親密度÷600（最大18%）を加え、全体上限72%とする

## A11. イベント・告白

イベントは、親密度が上がったから発生するキャラ側からの変化。通知、疑似LINE、疑似電話を組み合わせる。

告白の基本パターン:

1. イベント通知
2. 疑似LINEに入口メッセージ
3. キャラが「少し電話してもいい？」
4. ユーザーがOK
5. アプリ内疑似着信画面
6. 応答
7. 告白用の短い疑似電話
8. ユーザー選択
9. 結果反映

最初から着信ではない。ユーザーがOKした後で疑似着信にする。

### 告白の発生条件

以下の3条件をすべて満たしたときだけ候補になる。

1. 総合点が 1200 以上 … 関係全体がどれだけ進んだか
2. 共通ベースが 600 以上 … 時間の床。共通ベースは1日+5固定なので最低日数を保証する
3. 恋人スコアが 300 以上 … 会話の中身が恋愛方向であること

総合点だけの単一閾値にはしない。世間話や相談だけのユーザーが総合点で押し上げて届いてしまい、会話内容による差が消えるため。条件②と③は、どちらも現実的な利用の幅の中でボトルネックになりうる位置に置く。

あわせて、通話できるコイン残高があることを条件に加える。基準はA10-2の着信最低残高と揃える。

### 発生タイミング

条件が成立した時点で、1〜7日後のどれか1日をランダムに選んで予約する。毎日抽選する方式にはしない。外れ続けるといつまでも来ないユーザーが出るため。

予約した日が配信できない時間帯だった場合は、A10-2の配信ルール（現地8:00〜21:59、近接回避）に合わせて時刻だけ動かす。日付は動かさない。

点数も条件もユーザーには一切表示しない。ばらつかせるのは、呼び方の変化は画面に出るため、節目からの日数が毎回同じだと規則性が見えるからである。

### 通話にたどり着けない場合

- 着信をOFFにしているユーザーには、トークで告白する。通話を使わない
- 「電話していい？」を断る／無反応の場合は回数を消費せず、2日後にもう一度誘う。告白そのものが起きていないため
- 2回目も断る／無反応の場合はトークで告白に切り替える
- 保留のままユーザーが会話を始めた場合は、キャラ側から話を切り出す

最後の1つで「さっきの話は何？」と聞かれたかどうかをAIに判定させない。保留中は次に会話が始まった時点でキャラから切り出す。`event_states` の状態をLLM文脈へ渡すだけでよい。

着信のON/OFF設定は日常の気まぐれ着信に対するものであり（A10-1）、告白はユーザーがトークでOKを押してから鳴るため別に扱う。

## A10-5. 告白の返答

通話中に関係状態を確定させない。AIの判定を使わない。

1. 告白の通話では、キャラが告白し、ユーザーは普通に返事をする。ここでは何も確定しない
2. 通話終了後、そのキャラのトークへ選択肢付きの確認メッセージが1件届く
3. タップした内容だけが正。文字入力での返答は採らない

文字入力を採らないのは、AI判定が戻ることと、チャットのコイン消費が発生するためである。疑似LINE内の選択肢付き確認は、A9-1のモーニング登録確認とA11の「少し電話してもいい？」で既に必要な仕組みであり、新しい仕組みを足さない。

告白イベントは1つのキャラにつき最大2回。

- 1回目 … OK なら `lover`。断る／保留は `friend` へ戻す。恋人スコアはそのまま継続し、付け替えもしない。2回目がある
- 2回目 … OK なら `lover`。断る場合は打ち切り。`max(0, 恋人スコア − 友人スコア) × 50%` を友人スコアへ付け替え、恋人スコアを0にし、`romance_event_allowed` をOFFにする

1回目に「保留」を置くのは、ここで断ったら二度と告白が起きないと思われることを防ぐため。挙動は「断る」と同じでキャラの返し方だけが変わる。2回目は最終なので置かない。返答の種類で打ち切り判定を分岐させない。返答が明確とは限らないため。

2回目の条件は、恋人スコアが +60 増え、かつ会話した日で30日以上たつこと。日数だけで区切ると、断られたあと関係が冷めたユーザーにも機械的に2回目が来てしつこくなる。条件を満たしたら1回目と同じく1〜7日後のどこか1日で発生する。

確認メッセージの期限は3日とする。

- 放置はその回を消費する。期限切れで `expired` とし `friend` へ戻す
- 期限切れ後は選択肢のボタンを無効化する。遡って押せると「消費する」が成立しない。メッセージ自体は履歴に残す
- 返事待ちの間は気まぐれ着信を止め、デイリー枠だけにする。ゼロにはしない。アプリを開かないユーザーが期限切れに気づけなくなるため
- 返事待ちの間の文面は、待っている前提で作る。`relationship_state` が `romance_event_pending` になっているのでLLM文脈へ渡すだけでよい

断られた結果をキャラ性で変える（引き下がり方、打ち切り後の距離の取り方）のは、v1ではセリフと態度だけに適用する。数値は全キャラ共通とする。キャラごとに数値を持つと、付け替えの割合・2回目までの間隔・減点幅をキャラ数ぶん持つことになり検証も増える。

`romance_event_allowed` を「恋人候補」から「親友候補」へ切り替えた場合も同じ仕組みで付け替える。割合は `max(0, 恋人スコア − 友人スコア) × 25%` とし、打ち切り時より低くする。告白イベントは二人の間で実際に起きた出来事だが、設定の切り替えはユーザーが一人で操作しただけであり、関係の重みが違うため。切り替え前に「恋人としての進みが減る」旨の確認を出す。

付け替えを固定割合（恋人スコアの一定割合）にしないのは、カテゴリが混ざるため友人と恋人の比がユーザーごとに違うからである。相談・打ち明けが中心のユーザーは友人スコアの方が多くなる。差額方式なら友人スコアが恋人スコアを超えることが原理的に起きず、すでに友人の方が多いユーザーには何も足さない。

告白・関係変化・呼び方変更・強めのイベントは、ユーザーの明示同意を挟む。

- 関係状態変更: OK / 今のまま / 戻す
- 呼び方: OK / 今はやめる
- キャラが勝手に変更しない。同意前は `pending`
- 既読だけ・放置は同意ではない
- 未応答なら状態を戻す、または保留する
- しつこく迫らない

## A10-6. lover後

告白OKで関係状態 `lover`。

**告白がOKになったときの演出（未実装）**

- そのキャラのトーク画面で♡が舞う
- 名前の横にハートを付ける

loverは通知上も会話上も文脈が変わる。

lover後の過去イベントはrememberableにする。

口調・態度・通知の温度・疑似電話やモーニングの一言は、関係状態を `lover` としてLLM文脈に渡すことで自動的に恋人トーンになる。

無料ユーザーでもlover化可能。恋人化を有料限定にしない。

AI会話継続は通常どおりコイン消費。

## A10-7. 告白の課金

告白が始まった地点から1往復を課金対象外にする。通話の最初からではない。

対象は次の3つとする。

- 告白のセリフ
- ユーザーが返事をしている時間（ユーザーターンの経過時間）
- それに対するキャラの応答音声の再生時間

その次のやり取りから通常どおりコイン消費に戻る。

ユーザー発信の通話中に告白を切り出した場合も同じ。告白が始まるまでの部分は通常どおり課金する。ターンごとに時間を記録して通話終了時に精算する既存の仕組みで、固定音声を0msとして扱うのと同じやり方で実現する。

無料の1往復のあとに残高が尽きても、告白そのものは成立している。通話終了後に確認メッセージが届くので返事は選べる。

# A11. 安全・コンテンツ方針

## A11-1. 基本路線

健全路線。性的表現・過激表現は禁止。

告白OKで関係状態 `lover`。lover後の過去イベントはrememberableにする。

無料ユーザーでもlover化可能。恋人化を有料限定にしない。AI会話継続は通常どおりコイン消費。

## A12. 安全・コンテンツ方針

健全路線。性的表現・過激表現は禁止。恋愛は情緒的・日常的な範囲まで。

禁止:

- 性的描写 / 性行為 / 露骨な誘惑
- 未成年との恋愛・性的文脈
- 自傷・他害の助長
- 違法行為の助長
- 現実の人物へのなりすまし
- 依存を強める過度な束縛・罪悪感誘導

通知文にセンシティブ情報を出さない。恋愛関係でも、ロック画面通知で過度に親密・恥ずかしい文言を出さない。

自傷・他害・医療・法的相談などはキャラ人格より安全テンプレートを優先する。緊急時は公的窓口・地域別ヘルプに誘導する。

# B. 課金設計

## B1. 通貨単位

アプリ内通貨はコイン。ユーザー向け表示はコインで統一する。

## B2. 消費しないもの

- デイリー通知のAI生成
- 通知文
- 入口メッセージ
- 固定・テンプレ通知
- モーニングのAlarmKit音
- Good morning onlyの固定音声
- 通話前の最初の固定一言
- 特別イベント最初の固定一言
- 聞き取り失敗・無音・雑音の固定文言
- ランダム猫のAI不使用反応
- 日次処理の要約・分類
- エラー文言

通話では、次の待ち時間・固定音声の再生時間を課金対象時間へ含めない。

- 呼出中・接続前
- WebSocket接続待ち・通信待ち・再接続待ち
- STT処理待ち・LLM回答生成待ち・TTS生成待ち
- 音声ファイル取得待ち・アプリ側の処理遅延
- 固定の聞き返し音声・エラー案内音声の再生時間
- 通話前の固定音声・Good morning onlyの固定音声の再生時間

無音・聞き取り失敗として確定するまでのユーザーターン経過時間は課金対象である。その後に流れる固定の聞き返し音声の再生時間は課金対象外であり、両者を混同しない。

**アプリの不具合で成立しなかったターンは、ユーザーターン経過時間も課金対象にしない。** 返事のテキストが端末へ届いたのに、決めた時間（15秒）を過ぎても音が鳴り始めないターンを指す。この場合はそのターンを課金から外し、待ち続けずに通話を終える。聞き取り失敗は含めない。聞き取り失敗はサーバ側の処理が実際に走っており、こちらの費用も出ているためである。印は端末が自分で気づいたときにだけ付け、精算後の通話には付けない（**推測で課金しない**の裏返しとして、**推測で返さない**）。何回起きたかを数えられる形で記録し、異常終了そのものへの埋め合わせを設けるかは、発生率の実測後にF5で決める。

## B3. 消費するもの

- 文字チャットでAIが返答した時の、AI返信1回ごとの固定消費
- 通話中の各ユーザーターンの経過時間
- 通話中のAI通常回答音声が端末で実際に再生された時間
- AI猫がユーザー入力に対して感情分類して鳴き声反応を返す時

チャットは文字数上限を前提とし、入力・出力トークン数による細かな従量計算は行わない。通話は1応答ごとの固定消費にせず、ターンごとに記録した課金対象時間を通話終了時に合算し、1通話分を一括精算する。

固定文言はLLMを呼ばないので消費しない。固定文言にTTSを使っても、AI通常回答でなければ再生時間を加算しない。TTS生成失敗・再生失敗、および生成されたが再生されなかったAI音声は課金対象にしない。

## B4. 無料ユーザー

無料ユーザーに提供するもの:

- 1AIメインキャラ
- ランダム猫
- モーニング導線
- デイリー通知（原則1日1通。休眠が続く場合と、利用者が設定で連絡の量を少なめにした場合は毎日でなくなる。A10-2参照）
- 関係進行 / 告白イベント
- 毎日回復コイン

関係値進行や告白は有料限定にしない。AI会話量は無料回復コイン範囲に制限される。

## B5. 月額会員 / 定期コイン

サブスクは無制限ではなく、割安な定期コイン付与。

- 月額で一定数コインを付与
- 月額で付与されたコインに有効期限・繰り越し上限は設けない
- サブスク限定で追加キャラ枠・通知上限・一部イベント演出を優遇する余地を残す

## B6. キャラ枠課金

メインキャラ以外のキャラでAIを使うには、そのキャラを買い切るか、月額の2,000円以上の段に入る。買い切りとサブスクは別のものであり、同じ「枠」として扱わない。

- 無料ユーザーはAI利用可能なメインキャラを1つだけ選ぶ。メインキャラは枠を使わない
- ランダム猫はAIを使わないので無料付属・枠消費なし
- AI猫はAIを使うため、人間キャラと同じ扱いになる

### 買い切り

**枠を買うのではなく、そのキャラを買う。** 購入した時点で対象のキャラが決まっており、他のキャラには使えない。

- 買ったキャラは解約や期限の概念を持たず、関係値ごと残り続ける
- 価格は1体800円。**500円になるのは、月額の枠で使っていたキャラをそのまま続けるときだけ**である。月額に入っていても、別のキャラを増やすなら800円である
- 500円を用意した理由が「解約した利用者がそのキャラを残せるように」だからである。新しく増やすぶんまで安くすると、月額に入っている間はいつでも半額で増やせることになる
- ストアの商品は2つ用意し、続けるための購入かどうかで出し分ける。同じ商品に2つの価格は付けられないためである
- 500円で続けられるのは、解約を申し出てから終了日を経て14日までである。この期限を価格の下に出す。出さないと、あとで800円になったときに黙って値上げしたことになる
- **ストアには消耗型（Consumable）で登録する。** キャラは何体でも買えるためである。非消耗型にすると1つのApple IDにつき一生に1回しか買えず、2体目が買えない。そのぶんストアからの復元では戻らないので、戻すのは引き継ぎコードによる（B8）
- **キャラ画面に「追加できる枠が空いています」と出してはならない。** 買い切りには空き枠という状態が存在しない

### サブスク付属

- 月額2,000円で1人、3,000円で2人追加できる。500円・1,000円の段には付かない
- 表示は「キャラを1人（2人）追加できます」とする
- **追加したキャラの入れ替えは作らない。** 入れ替えはv2以降の候補とする（G章）

### 月額の乗り換え

月額は同時に1本である。iOSは4つを同じサブスクリプショングループへ登録してあり、Appleが同時に1本しか持たせない。Androidも1本にそろえ、購入時に乗り換えであることをPlayへ伝える。段を変えるときは新規契約ではなく乗り換えになる。

**切り替わる時期**

- **上げるときは即時、下げるときは次の更新日から。** Appleは下げるときを必ず次の更新日からにしており、変えられない。Androidも合わせる。合わせないと、同じ操作をしてOSごとに枠が減る日が変わる
- 検証ビルドだけは、下げるときも即時に切り替える。Google Playのテスト購読は数分で終了して更新しないため、次の更新を待つ切り替えは一度も成立せず、Androidで枠の減り方もコインも確認できないためである。**本番ビルドは次の更新日からのままとする**

**切り替える前に確認を出す**

今のプラン、新しいプラン、いつ変わるか、枠が減るなら何が起きるかを出す。押してから知るのでは遅い。画面に「段」「買い切り」という言葉を使わず、「月額プラン」「購入」とする。

**上げた月のコイン**

- **いまのプランの残り日数ぶんを差し引いて渡す。** 500円プラン（650コイン）に入った6日目に3,000円プラン（4,800コイン）へ上げるなら、残り25日ぶんの546コインを引いて4,254コインを渡す
- 差し引くのは**新しく渡す枚数から**である。すでに渡したコインは回収しない。使い切られていても成立し、残高がマイナスにならない
- **Appleの返金額は使わない。残り日数で計算する。** 返金額はアプリから取れないうえ数円ずれる。日数で計算すれば、購入前の確認に出した枚数と実際に渡す枚数が必ず一致する
- **Google Playでは差し引かない。** Googleは返金せず、残っているぶんを次の更新日を後ろへずらして返す。払った金額とコインの枚数が釣り合っているためである
- 購入前の確認に、差し引いた枚数と渡す枚数を出す。出さないと、少なく渡されたようにしか見えない
- 差し引かないと、2,000円プランに入った翌日に3,000円プランへ上げるだけで、約70円で3,000コインを持ち逃げできる。これは毎月繰り返せる

**下げて枠が減ったとき**

- 更新日までに、枠に入っている全キャラへ、いつ話せなくなるかを案内する
- 更新日に**全員**話せなくなる。空き枠が新しいプランの数だけ残る
- 14日以内にその空き枠へ選び直せば、関係値ごとそのまま続く。選ばなかったキャラは解約と同じ扱いでリセットする。**こちらで勝手に選ばない**
- 15日以降も空き枠は残り、好きなキャラをいつでも選べる（関係は最初から）。空き枠には、まだ持っていないキャラも選べる
- **空き枠があるあいだは、キャラ追加に値段を出さない。** 空き枠は支払い済みなので、選び直しは無料である。値段を出したまま無料で処理してはならない

### 解約したときの扱い

サブスクで追加したキャラにだけ適用する。買い切ったキャラは影響を受けない。

**解約を申し出た時点**

- 対象キャラのトークの**最下部に固定で案内を出す**。会話が進んでも常に最下部に出し続ける
- 内容は、いつ使えなくなるかと、続けて使うには購入が必要であること

**サブスク終了日**

- そのキャラとは会話できなくなる。トークは**閲覧のみ**になる

**終了から14日**

- トークを閉じ、関係値もリセットする
- 14日以内に買い切れば、関係値ごとそのまま続く。価格は500円
- 14日を過ぎてから買うと、関係値はリセット済みの状態から始まる。価格は一般と同じ800円になる
- 14日を過ぎたら案内の文言を切り替える。関係が残っている前提の案内を出し続けない

価格は原価から出したものではない。キャラを1人増やしてもこちらの費用はほとんど増えず、無料付与のコインは利用者ごとなので変わらず、増えるのは通知の生成ぶんで月に数円である。値ごろ感だけで決めた数字である。

## B7. RevenueCat app user id

RevenueCat app user id は `public.users.id` とする。

使わないもの:

- `auth.users.id`
- 端末ID
- GoogleアカウントID
- AppleアカウントID
- email

Supabase Auth anonymous session の `auth.users.id` は認証セッションIDであり、RevenueCat app user idには使わない。

RevenueCat購入確認・Webhook・復元処理は、最終的に `public.users.id` に対してコイン付与・キャラ枠付与を行う。

## B8. 購入復元

購入復元はRevenueCatで確認する。ただし、アプリ内データの復元は `public.users.id` に戻れるかどうかに依存する。

原則:

- 引き継ぎコードがある場合、旧 `public.users.id` に戻す
- その後、RevenueCat app user id も同じ `public.users.id` で扱う
- 引き継ぎコードなしで再インストールした場合、新しい `public.users.id` が作られる
- その場合、購入状態はRevenueCat上で確認できても、旧キャラ記憶・関係値・チャット履歴・コイン残高は原則戻らない

消耗型コインは、復元で再付与しない。RevenueCatイベントID・store_transaction_id・idempotency_keyで二重付与を防ぐ。

**買い切りのキャラも、ストアからの復元では戻らない。** ストアの商品を消耗型で登録するためである（B6。非消耗型にするとApple IDにつき一生に1回しか買えず、2体目が買えない）。買ったキャラは `character_slots` に残るので、戻すかどうかは `public.users.id` に戻れるかどうか、つまり引き継ぎコードがあるかどうかで決まる。コインと同じ扱いである。

### 引き継ぎと購入復元は別の機能

**引き継ぎコード**は、旧端末のアプリの中身を丸ごと新端末へ移す。キャラ・関係値・会話履歴・
設定・コイン・月額の枠を一緒に移す。移したあとは新端末が旧端末の続きになる。

**購入の復元**は、ストアにある有効な購入・契約を、いまのアプリの状態へ反映する。扱うのは
月額契約と、それに含まれる枠と、次回以降の月額コインの配り先だけである。キャラ・関係値・
会話履歴・設定は移さない。

**購入の復元だけで完全な引き継ぎができる形にはしない。** Apple IDを家族で共有している場合に、
他人のキャラや会話履歴を取れてしまうためである。

### 引き継がずに入れ直したとき

新しい `public.users.id` で、まっさらな状態から始まる。キャラも関係値も会話履歴も設定も
コインも新規で、旧端末の月額枠は自動では移らない。旧端末の状態はそのまま残る。

そのうえで、利用者は「購入を復元する」を実行できる。

### 月額契約の構成

**月額契約 ＝ 毎月のコイン付与 ＋ キャラ枠1つ**とする。**1契約につき1枠**であり、端末ごとに
1枠ではない。同じ契約を新端末で復元しても枠を増やしてはならない。

### 「購入を復元する」を押したとき

**`restorePurchases()` を呼ぶ前に、必ず確認を出す。** 押した時点では、旧側で枠が使われて
いるかどうかを知る手段が無い（ストアの購入情報は復元を呼んで初めて手元に来る）。よって
条件を付けず、次の1文を先に出す。

> **購入を復元しますか？**
> 他の端末で月額契約を利用している場合、月額枠はこの端末へ移り、現在利用している端末では
> その月額枠を利用できなくなります。

ボタンは**［復元する］［キャンセル］**。［復元する］を選んだときだけ `restorePurchases()` を
呼ぶ。［キャンセル］では何も変えない。

### 枠の移動

月額が新しい `public.users.id` へ移ったら、**旧側の月額枠を外し、新側へ付ける。**
両方に同時に存在させない。新しい契約を作るのではなく、同じ1契約の枠の置き場所が変わるだけで
ある。旧側で枠から外れたキャラは、契約が終わったときと同じ扱いにする。

**枠が移ることと、キャラが移ることは別である。** 旧側のキャラ・関係値・会話履歴は移さない。
よって確認の文言をキャラの名前で書かない（「この桜音に切り替えますか？」のようにしない）。

### 復元後のコイン

**移すかどうかを利用者に選ばせる。** 旧側には基本枠と買い切りのキャラが残るので、移さなくても
旧側でコインは使える。

> **現在のコインもこの端末へ移しますか？**
> 移したコインは、現在利用している端末では使えなくなります。

ボタンは**［コインも移す］［移さない］**。移す場合はコピーではなく**移動**とし、旧側は0に
する。二重に使えてはならない。

**移すときは、返金による未精算と返金回数も一緒に移す。** 正のコインだけ持って行き、未精算を
旧側へ置き去りにすることを許さない。置き去りにできると、返金して使い切ってから入れ直すだけで
踏み倒せる（B8-2）。

**毎日の無料コインは移さない。** 毎日配られてその日で失効するもので、新しい端末でも同じだけ
配られる。移す意味が無いうえ、移すと同じ日ぶんを新旧の両方が持つので、入れ直すだけで二重に
取れてしまう。旧側に残しても、その日のうちに失効する。

**通話の未精算がある場合は、コインを移す前に精算する。** 精算できない未精算が残るときは、
コインを移さずエラーで終える。旧側・新側とも移す前の状態のままにする。

**期限は設けない。** 「移さない」を選んだあとでも、後から移せる。ただし移せるのは、いま
月額契約を持っている経路の1本だけとする。A→B のあとに B→C が起きた場合、A→B は無効になり、
Bが後からAのコインを引くことはできない。この場合 A のコインは A に残り、C から辿って
集めることはできない。

### 月額コインの配り先

復元した時点で、**その月ぶんの月額コインを配り直さない。** 旧側へ既に配ってあるためである。
次の更新から新しい `public.users.id` へ配る。イベントIDによる二重付与の防止はそのまま使う。

### 復元の結果に出す文言

結果ごとに文言を変える。ひとつの文言で済ませない。何が起きたのか、次に何をすればよいのかが
変わるためである。

| 結果 | 文言 |
|---|---|
| 復元した | **月額契約を復元しました。** |
| 復元できる購入が無かった | **復元できる購入はありませんでした。** |
| すでに今の状態と同じ | **購入情報は最新の状態です。** |
| 通信・ストアの確認に失敗した | **購入情報を確認できませんでした。時間をおいてもう一度お試しください。** |

**「購入を復元する」の置き場所**

引き継ぎの画面へ置く。機種変更や入れ直しのときにしか使わないボタンをコインを買う画面に置くと、何のボタンか分からないまま押される。

- 消さない。買い切りのキャラと月額を取り戻す手段は、ストアの審査で必要である
- 移すのは引き継ぎの画面を作るときとする。それまではコイン画面に置いたままでよい。押しても消耗型コインは戻らず、二重付与も起きないため実害が無い

## B8-2. 返金

返金の申請はストアの画面から利用者が行う。アプリからは申請できず、こちらから止めることもできない。**こちらがやるのは、返金されたという知らせを受けて後始末をすることだけである。** AndroidもiOSも同じで、Appleは申請が審査されるぶん即時ではない。

後始末をしないと、買って、使って、返金する、を繰り返すだけでただで使える。課金でいちばん大きい穴である。

**見分け方**

返金は解約の申し出と**同じ種類の知らせで届く**（RevenueCatの `CANCELLATION`）。理由の欄が `CUSTOMER_SUPPORT` のものが返金である。買い切り（コイン・キャラ）にも届くので、月額の商品だけに絞る判定より前に見分ける。

**コイン**

- 返金されたぶんを減らす。まだ残っているぶんを消し、足りないぶんは**未精算**として持ち越す
- すでに使い切られていても取り返しにはいかない。使ったのは事実である。**残高はマイナスになる**（550買って200使っていたら −200）
- マイナスの間は通話も送信もできない
- 未精算は、**そのあと受け取ったコインから差し引く**。毎日の無料コインでも、買い直したコインでも、月額のコインでも同じである。手持ちがあるのに払わせないと、返金の直後にコインを買った利用者は6,000枚持っていても「未精算です」と言われ続け、1日18枚ずつ何日もかけてしか消えない。未精算は「使ったのに払っていない」ぶんであり、払える手持ちがあるなら払える
- 差し引く順番は通常の消費と同じにする（期限の近いものから、同じなら配った順）。無料分を特別扱いしない
- 手持ちで足りなければ、残りは未精算として持ち越し、案内も出したままにする
- 0になるとまた使える
- 未精算が残っている理由をコイン画面に出す。文言はこれとする

> 返金により、使用済みの◯◯コインが未精算となっています。受け取ったコインから差し引かれ、0になると再び利用できます。

**キャラ**

- 買ったキャラは**その場で手放す**。会話も関係値も消す。買い切っていないキャラを枠から外すときと同じ扱いである
- 据え置き期間は設けない。返金は稀であり、14日残す仕組み（トークの案内、期限の表示、買い直しの導線、毎日の掃除）に見合わない
- **返金された購入は二度と枠にしない。** 返金してもストアの購入履歴からは消えないため、記録しておかないと、次にアプリを開いたときの購入確認が「まだ枠になっていない取引」とみなして空き枠を作り直す。返金するたびにキャラが1体ずつただで増える

**購入停止**

- **6か月以内に2回**返金されたら、その時点から**3か月間**購入できなくする
- 3か月が明けたあと**1年間**は、返金1回で即3か月の購入禁止とする。1年を過ぎたら「6か月で2回」に戻す
- 禁止のあいだは、コインも月額もキャラも買えない。**未精算があっても買わせない。** 買って埋められるなら、使ったぶんを払わずに済ませた人が金で抜けられる
- 返金の取り消しが届いたぶんは数えない。返金が無かったことになる以上、それを理由に止め続ける筋が無い
- 画面に理由と、いつまでかを出す。回数そのものは出さない

> 返金があったため、◯月◯日まで購入できません。

- **入れ直しによる周回は、この工程では止めない。** 止める手段はある（Androidは Play Integrity API の device recall、iOSは DeviceCheck。どちらも入れ直しや初期化のあとも端末を見分けられる、繰り返しの悪用を止めるための公式の仕組みである）。ただし両ストアでの設定と、こちらのサーバー側の作りが要るため、別の工程として出す前までに入れる。**入れないと、この節の購入停止は入れ直しで丸ごと消える**

### 返金の取り消し

Appleは、利用者の異議申し立てによって、一度出した返金を取り消すことがある（`REFUND_REVERSED`。Appleのみ）。Appleの資料に**「返金を理由にコンテンツやサービスを取り上げた場合は、元に戻す必要がある」**と書かれており、扱わない選択は無い。**取り消せる期間は書かれていない。**

- コイン、未精算、返金の回数、キャラの所有を元へ戻す
- 未精算がすでに埋まっていたぶんは、コインとして返す。埋めたのは利用者の手持ちであり、取り消された以上そのままにはできない
- **会話と関係値は戻らない。** 返金の時点で消しているためである。**Appleが戻せと言っているのは買ったもの、つまりキャラの所有であり、会話履歴は買ったものではない。** これで要件は満たす
- 二度戻さない

## B9. 引き継ぎ失敗時の扱い

引き継ぎ失敗例:

- コード期限切れ
- コード使用済み
- 入力ミス
- 旧端末が手元にない
- RevenueCatでは購入済みだが、旧 `public.users.id` に戻れない

方針:

- 引き継ぎコードなしでは、旧キャラ記憶・関係値・チャット履歴・コイン残高は原則戻せない
- 購入済みのサブスクはRevenueCatで確認し、現在の `public.users.id` に反映する余地を残す
- 買い切りのキャラはストアからの復元では戻らない（B8）。引き継ぎコードで元の `public.users.id` へ戻れた場合だけ戻る
- 消耗型コインは二重付与防止を優先する
- ユーザーに「引き継ぎコードなしでは会話履歴や記憶は戻せない」ことを明示する

## B10. コインが足りないときの表示と導線

### 残高の常時表示

コイン残高は、トーク一覧・キャラ・設定に加えて**会話画面の上部にも表示する**。会話画面だけ
残高が見えないと、通話ボタンを押すまで足りないことが分からないためである。

### 1件ごとの消費は出さない

**出すのは残高だけとする。** トークのタイムラインへ、1回ごとに使ったコインの枚数も、通話の
時間も出さない。時刻の横にも、通話の見出しの中にも置かない。

枚数を出さないのは、毎回「−3」「−14」が並ぶと使い控えにつながるためである。通話は1件で
10コイン以上、チャットは3コインなので、並べると通話だけが目立つ。通話を主にしたアプリで、
通話の値段が毎回目に入る形にしない。

時間も出さない。通話には**実際の時間**（開始から終了まで）と**課金された時間**（利用者が
話したターンとキャラの声が鳴った時間の合計。処理待ちを含まない）の2つがあり、実測では
5分29秒の通話で課金は2分1秒だった。どちらを出しても、もう片方と食い違って見える。
差の説明を添えなければ正しく伝わらず、タイムラインの1行に収まらない。

`coin_consumptions` には1件ずつ記録が残っており、必要になれば出せる。**記録を取るのをやめる
わけではない。**

### 足りないまま操作したとき

通話ボタンまたは送信ボタンを押した時点で残高が足りない場合、**「コインが足りません」と
「コインを買う」導線を同じ場所に出す**。必要な枚数（通話10コイン、チャット3コイン）は
文中に書かない。残高が常時見えているためである。

チャットは**送信そのものを止める**。発言を保存して返信だけ来ない形にしない。このとき
**利用者が入力した文章を消さない**。

### 残高が足りなくなって通話が終わったとき

通話画面に留めず、**自動でトーク画面へ戻す**。利用者が自分で切ったときと同じ動きにする。
切れる前に予告の音声を必ず1回流しており、理由はその時点で伝わっているためである。

トークのタイムラインへ、キャラの発言ではないお知らせを1枚置く。

> コインが足りなくなったので通話を終了しました ／ [コインを買う]

タイムラインに残すのは、数秒で消える帯だと購入導線を押しそびれるためである。**1キャラに
つき1枚までとし、新しく出すときは古いものを消す**（A9-1のモーニング確認カードと同じ）。

### 「なくなった」と書かない

文言は「なくなった」ではなく**「足りなくなった」**とする。話せる時間は課金単位の切りの
よいところで終わるため、残高が0にならず端数が残ることがある（例: 25コインで通話を始めると
150秒＝22コインを消費し、3コイン残る）。「なくなった」と書くと、残高表示との食い違いに
気づかれる。

### コインを買う画面

[コインを買う]の飛び先となる購入画面は未実装である。実際につながるのは購入導線
（RevenueCat）を作る工程とする。文言と置き場所だけを先に定める。

# C. アカウント・引き継ぎ設計

## C1. 基本方針

ログイン画面を作らない。

初回起動時にSupabase Auth anonymous sessionを自動作成する。

アプリ内ユーザー主キーは `public.users.id`。

`auth.users.id` は `public.users.auth_user_id` にだけ紐づける。

## C2. 匿名セッション / Supabase client制約

起動時に既存セッションがなければ `signInAnonymously()` を実行する。

Supabase local config と本番Dashboardの両方で Anonymous sign-ins を有効化する必要がある。

匿名セッション作成に失敗した場合は、初期化エラーとして扱う。ログイン画面へ逃がさない。

Supabase client初期化時、env未設定なら空文字で初期化しない。明示的にErrorを出す。

`onAuthStateChange` 内ではDB queryを直接awaitしない。セッション状態を更新した後、別非同期処理で `public.users.id` 解決とユーザーデータロードを行う。

古いload結果で新しいセッション状態を上書きしない。load sequence等で最新の読み込みだけを反映する。

# C3. `auth.users.id` と `public.users.id`

`auth.users.id` は認証セッションID。

`public.users.id` はアプリ内ユーザーID。

解決経路:

```text
Auth session
  auth.users.id
    ↓ user_auth_links.auth_user_id または public.users.auth_user_id
  public.users.id
    ↓
  settings / coin_balances / user_characters / chat_messages / calls / user_character_memory / revenuecat_events / coin_transactions / coin_lots / coin_consumptions
```

各ユーザー別テーブルの `user_id` は `public.users.id` を参照する。

アプリ側にはservice role keyを置かない。

アプリ側はanon / publishable key + RLS前提で動かす。

service role相当の権限が必要な処理は、Edge Functionまたはsecurity-definer RPCへ閉じる。

# C4. 初回ユーザー作成

Authユーザー作成時triggerまたは初回データロードで自動作成するもの:

- `public.users`
- `public.settings`
- `public.coin_balances`

自動作成しないもの:

- `notification_preferences`
- `user_characters`
- `character_relationships`
- `user_character_memory`
- `device_installations`

これらは初回オンボーディングや端末登録時に作成する。

## C5. 端末インストール管理

`device_installations` を持つ。

目的:

- push token管理
- 端末別通知許可状態
- 同一ユーザーの複数端末管理
- 引き継ぎ後の二重通知防止
- 退会時の端末無効化

同じ `public.users.id` に複数端末が紐づく可能性を許容する。

## C6. 引き継ぎコード発行

旧端末で引き継ぎコードを発行する。

- 生コードはDBに保存しない
- DBには `code_hash` のみ保存
- 有効期限を持つ
- 単回使用
- 発行者の `auth.users.id` を保存
- 対象の `public.users.id` を保存
- 発行処理はEdge Functionまたはsecurity-definer RPC経由
- クライアントが `transfer_codes` を直接insert/select/updateしない

## C7. 引き継ぎコード入力

新端末で引き継ぎコードを入力する。

流れ:

1. 新端末で匿名セッション作成
2. 新しい仮 `public.users.id` が作成される
3. 引き継ぎコード入力
4. サーバ側でコード照合
5. 有効期限・使用済み・ハッシュ一致を確認
6. 旧 `public.users.id` に戻す
7. 新端末の `auth.users.id` を旧 `public.users.id` と紐づける
8. 仮ユーザーを無効化または削除候補にする

RLS上の現在ユーザー解決は、原則 `user_auth_links.auth_user_id = auth.uid()` かつ `is_current = true` を使う。

`users.auth_user_id` は現在代表リンクのキャッシュまたは単一現行セッション用の互換カラムとして扱う。矛盾時は `user_auth_links` を正とする。

引き継ぎ完了時は旧端末リンクを `is_current = false` にする。複数端末を許す場合でも、通知対象は `device_installations` で制御し、RLSのユーザー解決と通知送信先を混同しない。

## C8. 再インストール時

引き継ぎコードなしで再インストールした場合、新しい匿名ユーザーになる。

旧チャット履歴・記憶・関係値・コイン残高は原則戻せない。

購入状態はRevenueCatで確認できる場合があるが、アプリ内データ復元とは別問題。

## C9. 退会・削除

退会時に削除するもの:

- 会話
- 記憶
- 行動ログ
- 通知候補
- 端末トークン
- キャラ関係状態
- コイン残高と利用権（購入分を含む残りの全コインを0にし、払い戻し・移動・復元はしない）

保持または匿名化するもの:

- 購入ログ
- RevenueCatイベントログ
- 監査用の最低限ログ

有償コインのロットは残数を0にしたうえで、購入・返金・二重付与防止・不正利用対応の監査用に保持する。毎日の無料コインなど無償ロットは削除する。保持する記録は氏名・認証情報から切り離し、新しい匿名ユーザーの残高には戻さない。

退会後に同じ端末で起動した場合、新しい匿名ユーザーを作る。退会済みユーザーの引き継ぎコードは使えない。

# D. DB設計

## D0. DB全体方針

`public.users.id` がアプリ内user_id。

`public.users.auth_user_id` が `auth.users(id)` を参照する。

他テーブルの `user_id` は `auth.users(id)` ではなく `public.users(id)` を参照する。

古いmigrationに `relationships.user_id references auth.users(id)` のような記述が残っている場合は、v4方針と衝突するため整理対象。

RLSは `auth.uid()` から `public.users.id` を解決して判定する。

RLS上の現在ユーザー解決は、`user_auth_links.auth_user_id = auth.uid()` かつ `is_current = true` を正とする。

`users.auth_user_id` は、現在の代表リンクを参照するキャッシュまたは互換カラムとして扱う。

`users.auth_user_id` と `user_auth_links` が矛盾した場合は、`user_auth_links` を正とする。

引き継ぎ時は新しい `auth_user_id` のリンクをcurrent化し、旧リンクは必要に応じて `is_current = false` にする。

# E. 記憶設計

## E1. 4層の記憶

1. 画面履歴

- チャット本文
- 通話見出し
- 90日で自動削除
- 重要なものはピン留めで残せる

2. 夜間処理後の未整理文脈

- 最後に成功した夜間処理より後のチャットログ
- 通話終了後に作った正式な通話要約
- 現在の通話内の直近履歴
- 同日短期文脈専用テーブルは作らない
- チャットは通常すべて渡し、最大20,000文字。超過時は新しい会話を優先する
- 未整理の通話要約は1本最大1,000文字、合計最大5,000文字

3. 日次要約

- ユーザー×キャラ×日付ごとに夜間処理で作る
- その日の会話の流れを400〜800文字、最大1,000文字へまとめる
- 直近7日分をAIへ渡す
- 作成から7日で削除する
- 会話が無かった日は作らない

4. 長期記憶

- キャラが長期間覚える必要がある、特に重要な要点・状態
- `user_character_memory` に保存
- 恒久保存

長期記憶例:

- 呼び方
- 好き嫌い
- 生活リズム
- 重要イベント
- 関係状態
- 禁止事項
- 安全フラグ

## E2. 通話ログ保存

通話中は `call_logs` に確定テキストとAI応答テキストを保存する。

音声ファイル保存は必須ではない。

課金・誤課金防止のため、各ターンの録音開始から終了確定までの経過時間と、AI通常回答音声の実再生時間を保存する。固定の聞き返し音声・エラー案内音声の再生時間はAI通常回答音声の実再生時間へ含めない。

通話終了時に同じ`call_id`の保存済み計測記録を合算して一括精算する。強制終了・異常切断・通信断で終了処理が完了しなくても、未精算通話を確認して回収・再試行でき、二重精算しない構造にする。

通話終了後、保存済み全文から正式な`call_summaries`を非同期生成する。要約生成をユーザーに
待たせない。次のチャット・通話は、日次要約へ未反映の正式な通話要約を文脈へ加える。

同じ通話が長くなり、現在の通話内履歴が10往復または12,000文字へ近づいた場合は、古い部分
だけを通話中の一時要約へまとめ、最近の会話は原文のまま残す。一時要約はその通話内だけで使い、
通話終了時に破棄する。正式な通話要約は一時要約からではなく保存済み全文から作る。

夜間処理成功後に `daily_summaries` / `user_character_memory` へ反映し、処理済み`call_logs`の
本文を削除する。正式な通話要約、未処理の通話本文、日次要約はいずれも作成から最大7日保持する。
処理失敗中の通話本文は翌日へ繰り越すが、7日を超えて本文を保持しない。

## E3. 日次処理

対象:

- その日の日次処理ウィンドウ内のchat_messages
- call_logs
- 通話終了後に生成済みのcall_summaries
- event_states
- notification_logs

通話がどの日のものかは終了時刻で決める。開始時刻は使わない。疑似LINEの通話見出しが終了時刻の位置へ差し込まれるため、画面上の並びと日次処理の帰属を一致させる。日付をまたいだ通話も分割せず、終了時刻の日へまとめて入れる。

処理単位はユーザー×キャラ×日付とする。同じユーザーでもキャラごとに入力・出力を分離し、
別キャラとの会話や記憶を混ぜない。会話量がモデル入力上限を超える場合だけ分割する。

日次処理は既存の毎晩の自動実行へ相乗りし、日本時間03:30の異常通話回収後に開始する。
一時的な通信失敗、タイムアウト、AIサービス側エラーは、失敗した処理単位だけ同日04:00と
05:00に再試行する。入力不正など再試行不能な失敗は同日に繰り返さない。2回の再試行でも
失敗した処理単位は元の日付を維持して翌日へ繰り越し、別の日付の処理を止めない。

出力:

- daily_summaries
- user_character_memoryの更新
- relationship/intimacy補正候補
- 翌日以降の通知材料

日次処理でやらない:

- 次の日の通知文を全部確定
- 長期記憶の間引き
- 自動のキャラ関係変化確定
- 自動恋人化

## E4. AIに渡す文脈

毎回固定で渡す:

- キャラpersona
- 関係状態
- 呼び方
- 長期記憶（ユーザー理解シート5種類すべて）
- 直近7日分の日次要約
- 現在日時(日付・曜日・時刻)

現在日時はユーザーの`settings.timezone`で解決した現地時刻を渡す。サーバー時刻をそのまま渡さない。時刻を渡すのは、朝・昼・深夜で会話の内容が変わるためである。通話中はターンごとに更新し、日付をまたぐ長時間通話でもずれないようにする。

「明日」「先週」のような相対表現はそのまま保存しない。記録時に絶対日付へ変換する。相対表現のまま長期記憶へ入れると、読むたびに解釈が変わり、毎日「明日プレゼンがある」と言い続けるような破綻が起きる。

状況で渡す:

- 最後に成功した夜間処理より後のチャットログ（最大20,000文字）
- 日次要約へ未反映の正式な通話要約（1本最大1,000文字、合計最大5,000文字）
- 通知/イベント文脈
- 今の通話内の直近履歴
- 長い通話で作った、その通話内だけの一時要約
- 関係変化/告白pending状態

渡さない:

- 全履歴全文
- 古いログ全部
- 不要なセンシティブ情報

## E5. 長期記憶更新

AIに自由に記憶を決めさせない。

AIは候補抽出・分類だけ。

サーバ側ルールで採用/不採用を決める。

採用ルール:

- 好み・出来事は1回の言及で採用する。
- プロフィール(仕事・家族・住まい)は2回言及されてから採用する。誤って覚えたときに会話が壊れる度合いが大きいため。
- 「その話はやめて」に類する要求は1回で即採用し、自動では消さない。嫌なことを2回言わせない。
- ユーザーによる明確な否定は、種類を問わず1回で反映する。

既存の記憶と食い違う発言があったときの扱い:

- 好み・趣味・持ち物など本人が話しやすい話題は、会話で確認してよい。確認は1日1件までとする。取り調べのように繰り返さない。
- 家族・健康・仕事を失う話・住まいの変化は確認しない。黙って新しい内容へ更新する。失った話を確認で掘り返さない。
- 確認して答えが得られない場合は両方を残して「未確定」とし、AI側からその話題を持ち出さない。
- ユーザーが自分からその話題を出した場合は、触れられた側だけを確定にする。もう一方は未確定のまま残す。
- 記憶を消すのは、ユーザーがはっきり否定したときだけとする。

ユーザーに見せる/消す機能はv1では最小。v2で詳細管理。

# F. 開発中に決める数値・検証項目

F章に残すのは、今決めなくても実装順が崩れないものだけ。

## F1. コイン数値

2026-08-05に、原価の実測をもとにすべて確定した。

### 消費

- チャット1往復（AI返信1回）: **3コイン**
- 通話: **60秒までで10コイン。以後は30秒ごとに4コイン**

通話は1回ごとに、AIが文脈を読み直す高いターンが1度だけ発生する。60秒までを10コインの
最低消費にしているのはこれを吸収するためであり、短い通話を割高に見せるためではない。

### 無料付与

- **1日18コイン**
- **翌日へ繰り越さない。毎日18コインへ戻す**

18コインは、通話を1回だけできる枚数である。20コインにすると60秒の通話が2回でき、
1回ぶんの高いターンを2度払うことになるため、同じ枚数あたりの原価が跳ねる。
18で止めるのはそのためである。

繰り越さないのは、貯めれば1日に18コインを超えて使える日が作れてしまい、無料の範囲で
関係の進むペースを上げられるためである（A5-2の会話量2段階の境界は19コイン）。

### 買い切り（有効期限なし）

| 価格 | 枚数 |
|---|---|
| 500円 | 550枚 |
| 1,000円 | 1,250枚 |
| 3,000円 | 4,200枚 |
| 5,000円 | 7,500枚 |

1円あたりの枚数を段ごとに変えてある。単一の比率にすると「1コイン＝1円」で換算され、
単価比較だけで購入可否を判断されるためである。

### 月額（付与されたコインの有効期限なし）

| 価格 | 枚数 |
|---|---|
| 500円 | 650枚 |
| 1,000円 | 1,400枚 |
| 2,000円 | 3,000枚 |
| 3,000円 | 4,800枚 |

買い切りより1円あたり約1割多い。月額は定期的に受け取る代わりに単価を低くし、買い切りは
必要なときだけ購入できる。どちらで付与されたコインも時間経過では失効しない。

### 有効期限と払い戻し

- 買い切り・月額で有償付与されたコインは、時間経過では失効しない
- 毎日の無料コインは翌日に繰り越さず、日付が変わると失効する
- 任意の退会時は購入分を含む全残高を消滅させ、払い戻し・別アカウントへの移動・復元をしない
- 上記を利用規約、コイン画面、退会確認画面に明示する

有償コインを無期限とするため、前払式支払手段への該当性、届出・表示・供託等の要否を
リリース前に法務・会計の専門家へ確認する。期限を付けて義務を回避する前提では運用しない。

### 根拠（2026-08-05の実測）

1コインの原価は約 **$0.00042（約0.065円）**。この値は次の実測から出している。

| 項目 | 実測値 | 出どころ |

| 課金時間のうちユーザー発話 | 59.6% | 同上 |
| 通話1ターンのLLM（2回目以降） | $0.00021 | staging `voice-turn` のusage実測 |
| 通話1ターンのLLM（通話の1回目） | $0.00127 | 入力6,128トークン実測×公表単価 |
| チャット1回（連続） | $0.00037 | staging `chat-reply` のusage実測 |
| チャット1回（久しぶりの1通目） | $0.0012 | 同上 |

| 音声合成 | $0 | オンデバイス |
| LLM単価 | 入力$0.20 / キャッシュ$0.02 / 出力$1.60 | gpt-5.4-nano 公表価格 |

チャットは連続して送るとキャッシュが効いて3分の1になる。単発で送られる回がいちばん高く、
無料枠の原価はこの単発を上限として見積もっている。ストア手数料は年商1億円以下なら
AppleもGoogleも15%である（Appleは小規模事業者プログラム、Googleの定期購読は最初から15%）。

### 端数の扱い・最低残高・繰り越し

- **端数は切り上げる。** 61秒の通話は14コイン、91秒は18コイン。書いたとおり「30秒ごとに
  4コイン」に動く。切り捨ては利用者に得だが、説明した動きと違うため不信を招く
- **通話開始には10コインが必要。** 1課金単位（60秒ぶん）を持っていない状態で通話を始めない
- **買い切り・月額の未使用分は期限なく繰り越し、枚数の制限は設けない**
- **無料付与は繰り越さない。使い残しても翌日は18コインへ戻す**

端数の向きは採算をほとんど動かさない。1コインの原価0.065円に対し売値は0.8円で、10倍以上の
開きがあるためである。効くのは無料枠だけで、切り上げなら18コインで最長2分・月38円、
切り捨てなら最長2分29秒・月45円となる。切り上げを採るのは説明との一致を優先したためで、
費用のためではない。

保有できるコインの総量に上限は設けない。上限を置くと、超えた利用者は買えなくなる。
有償分は蓄積し得るため、未使用残高を会計・法務上の管理対象として集計する。異常な残高は
上限で止めるのではなく記録して検知する。

- 通知重み（A10-2分はv5.35で確定。イベント等の共通重みは未決）

会話量2段階の境界は**19コイン**、倍率は**×2.0**で確定した（A5-2）。共通ベースの上乗せも
同じコイン量で測り、19〜36コインで **+1.5**、37コイン以上で **+3** とする（A5-2）。

## F3-2. 利用者からの告白（2026-08-04 方針決定・実装は別工程）

A11の告白イベントはキャラ側から起こすものだけを定めており、利用者が自分から気持ちを伝えた
場合の扱いを決めていなかった。実機確認で指摘があり、**利用者からの告白も恋人へ進める道として
受ける**ことを決定した。何か月も関係を積み上げた利用者が自分から伝えても素通りするのは不自然
であるため。実装は別工程で行う。

### 守る前提（A10-5の既決事項をそのまま適用する）

- 関係状態は**通話中に確定させない**。確定はトークの選択肢のタップだけで行う
- AIの判定を関係状態の根拠にしない。AIにできるのは「告白らしき発言があった」の検出までで、
  それは確認メッセージを出す引き金にしかならない

### 発生条件

- **キャラ側の告白と同じ3条件**（総合1200・共通ベース600・恋人スコア300）を満たすときだけ受ける
- 満たさないときは**確認メッセージも選択肢も出さない**。キャラは会話として軽く受け流す
- 2回の告白を断り切った後は、恋人スコアが0になり恋愛イベント許可もOFFになるため、
  この条件で自動的に受け流される。専用のルールは要らない
- 恋愛イベント許可がOFFのキャラは恋人スコアを積まないため、同じく受け流される

### 成立

- 条件を満たしていれば**必ず成立する**。キャラは断らない。利用者が自分から伝えている以上、
  そこで断られる体験は求められていない
- **キャラ側の告白回数（最大2回）には数えない**。あの回数はキャラから何回誘えるかの上限であり、
  利用者からの告白はその枠外である

### 確認メッセージの選択肢

キャラ側の告白と選択肢の意味が違う。ここを取り違えないこと。

| | 選択肢の意味 |
|---|---|
| キャラ側の告白 | **利用者の返事**（うれしい／ごめんなさい／少し考えたい） |
| 利用者からの告白 | **本人確認**（そう伝えた／そうじゃない） |

「そう伝えた」を押した時点で `lover` になる。確認を挟むのは、AIの誤検出だけで恋人になることを
防ぐためである。会話の流れで「好き」に近い言葉が出ただけで成立してはならない。

### キャラ側の告白と重なったとき

| 状況 | 扱い |
|---|---|
| 条件成立後、キャラ側の告白が予約されている（まだ発生していない） | **利用者側を優先して成立させ、予約中のイベントは取り消す**。恋人になった後にキャラから告白が来るのは不自然なため |
| キャラが「電話していい？」と誘っている最中、または3択を出して返事待ち | **そちらを優先し、利用者からの告白は受けない**。進行中の告白を同時に2つ走らせない（`event_states` の一意制約と揃える） |

### 未決

- 検出の条件。AIの分類に頼る以上、誤検出は起きる。確認メッセージが不要に出る頻度を
  どこまで許容するか。検出をどの層（voice-turn / chat-reply / 夜の日次処理）で行うか

# H. 検証済み前提

## H1. 声モデル

AivisHub上で商用利用可能なACML 1.0モデルを確認済み。アプリへの組み込み・再配布が可能であることを確認済み(桜音モデルで確認)。

利用条件:

- 声モデルの配布(ダウンロード)にライセンス文書を同梱する。
- 非公式かつ本人(声の提供元)とは無関係である旨を表記する。

v1仮採用:

- 女性: まお / コハク / 桜音
- 男性: にせ / fumifumi / 猩々博士

オンデバイスTTSは上記6キャラ全員に適用する。桜音1モデルに絞る前提にはしない。方式・量子化(動的INT8)・配信(Cloudflare R2)が実際に成立するかを確認するための検証・テストの基準モデルとして桜音(AIVMX)を用いる。方式・量子化・配信はA8-3を正とする。

## H2. iOSモーニング

iOS AlarmKit検証済み。カスタムAlarmKit音やアプリ内Web Audioループ音はv1対象外。

## H3. Androidモーニング

Android実機のPhase0検証（テスト機1台）で、設定画面表示中を含むfull-screen intentによる疑似着信表示、疑似着信音、通知の`応答`からのAI通話、AI第一声、固定メッセージの通常通話画面と近接消灯まで成立した。近接消灯は固定音声開始後だが従来より早くなり、現段階の機能として採用した。Androidモーニングの機能実装はこの端末で完了とする。音はActivityではなくForeground Service側で鳴らし、全画面表示と音を分離する方針。

ただしこれは1機種でのPhase0結果であり、全メーカーでの動作は未確認。Android 14以降の `USE_FULL_SCREEN_INTENT` 権限が実効的に付与されない場合や、メーカー独自の自動起動・バックグラウンド起動制限により、full-screen intentが出ず通知バナーのみ・無音になる端末が存在しうる。

方針:

モーニングは特定メーカーだけで成立すればよいものではない。

メーカー差で全画面が出ないことを「許容範囲」で済ませない。

full-screen intentの実効付与とメーカー別の自動起動制限は、本番前の要検証・未解決事項として扱い、F7で検証する。

## H4. 疑似電話TTFA

Android実機で STT → LLM → Aivis TTS(クラウド) → 音声再生まで成立し、TTFA約2秒前後を確認した実績は、オンデバイスTTS採用前の履歴としてのみ保持する。このクラウドTTS経路は正式な最終構成には含めない。

その後、TTSはオンデバイス化を採用決定(A8-3)。オンデバイスTTSの実測(POCO X6 Pro / CPU EP 4スレッド、桜音を基準モデルとして計測)は、1文目の再生開始まで約0.9〜1.0秒(文末単位ストリーミング)、INT8化による音質劣化なし。以後のTTFA前提はオンデバイスTTSだけを基準にする。
