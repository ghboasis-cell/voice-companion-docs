# 0. v4.0の前提

## 0-1. 正本ルール

- この仕様書は「何を作るか」を定義する。
- 作業順、PR方針、検証手順は `voice_companion_build_plan.md` で管理する。
- 過去スレの断片や旧メモは正本として扱わない。

## 0-2. ログイン画面なし

VoiceCompanion v1はログイン画面を持たない。

初回起動時、アプリはSupabase Authの匿名セッションを自動作成する。ユーザーに見せる最初の体験は、ログインではなく名前入力とキャラ選択である。

## 0-3. アプリ内ユーザーID

アプリ内ユーザー主キーは `public.users.id` とする。

`auth.users.id` はSupabase Authの認証セッションIDであり、各ユーザー別テーブルの `user_id` として直接使わない。

各ユーザー別テーブルの `user_id` は原則 `public.users(id)` を参照する。

## 0-4. 引き継ぎ

端末変更・再インストール時のアプリ内データ引き継ぎは、Google / Apple / emailログインではなく、引き継ぎコードで行う。

旧端末で引き継ぎコードを発行し、新端末で入力することで、同じ `public.users.id` へ戻す。

引き継ぎコードなしでアプリを削除・再インストールした場合、アプリ内データは原則復元できない。

## 0-5. 本番導線から削除するもの

以下はv1本番導線から削除する。

- Googleログイン
- Appleログイン
- email/passwordログイン
- ログイン画面
- OAuth callback deep link
- SocialLogin依存
- Google client ID前提の本番ログイン
- Apple Sign In capability前提の本番ログイン
- `auth.users.id` をアプリ内ユーザー主キーにする設計
- `RevenueCat app user id = auth.users.id` の設計

email/passwordは過去のデバッグ疎通実績としては残るが、本番導線では使わない。

# A. 体験仕様

## A1. アプリの核

VoiceCompanionの核は「AIと、アニメ声で会話する」こと（文字・音声）である。

恋愛・告白は後から乗った付加要素であり、アプリの核ではない。

優先順位は「会話×アニメ声＝主／恋愛＝従」。

実装で迷ったら、会話・アニメ声・キャラが日常に現れる体験を優先し、恋愛要素は削る/後回しにする判断もあり得る。

VoiceCompanionは、ユーザーが自分から開いて話すだけのAIチャットではなく、AIキャラ側からユーザーの日常に現れるアプリである。

ただし通知専用アプリではない。ユーザー発信の疑似LINE・疑似電話も、関係行動として扱う。

主な入口:

- モーニングコール
- デイリー通知
- 気まぐれ通知
- イベント通知
- 特別イベント疑似着信
- 疑似LINE
- 疑似電話
- ランダム猫 / AI猫

AlarmKitやAndroid full-screen intentは、この体験を成立させる実装手段であり、アプリ価値そのものではない。

## A2. v1 MVPスコープ

v1に入れるもの:

- ログイン画面なしの匿名セッション自動作成
- 初回名前入力
- 初回キャラ選択
- 初回好意度/第一印象選択
- 引き継ぎコード発行
- 引き継ぎコード入力
- 人間キャラの選択肢
- 複数キャラ保有構造
- 無料/有料によるAI利用キャラ枠
- ランダム猫 / AI猫
- 疑似LINE
- 疑似電話
- モーニングコール
- デイリー通知 / 気まぐれ通知 / イベント通知
- 通知ON/OFF、サイレント時間帯
- iOS 26以上のAlarmKit導線
- Android full-screen intent notificationを第一候補にしたモーニング導線
- キャラごとの通知ON/OFF
- 告白イベント
- チャット本文・通話見出しの90日自動削除＋ピン留め
- キャラの長期記憶
- コイン/従量課金
- キャラ枠課金
- 月額コインパック
- RevenueCat連携
- サーバ側コイン管理 / 消費ログ

v1から外すもの:

Google / Apple / emailログインは「v1ではやらない候補」ではなく、現行v1方針から削除する本番導線である。将来の任意バックアップ用途はv2以降候補に回す。

## A3. 初回起動・オンボーディング

初回起動時の流れ:

1. アプリ起動
2. Supabase anonymous sessionを自動作成
3. `auth.users.id` から `public.users.id` を解決
4. `public.users.display_name` が未設定なら名前入力へ進む
5. キャラ選択へ進む
6. 初回好意度/第一印象を3段階で選ぶ
7. `user_characters` と `character_relationships` の初期行を作成
8. 必要に応じて `user_character_memory`、`notification_preferences`、`device_installations` を作成
9. 疑似LINEホームへ進む

## A3-2. 名前入力

初回に必須なのは氏名または名前のみ。本名である必要はない。

呼び方の初期指定UIは置かない。呼び方は関係進行で変わる体験として扱う。

## A3-3. ログイン画面を出さない

初回起動時にログイン画面は出さない。

セッション作成中は、短い準備中表示のみとする。失敗時は、通信エラーまたは初期化エラーとして扱い、Google/Apple/emailログインへ誘導しない。

## A3-4. 再起動時

既存匿名セッションが残っている場合、そのまま同じ `public.users.id` を解決する。

セッションが失われた場合、新しい匿名ユーザーが作られる。旧データに戻るには引き継ぎコードが必要。

## A3-5. 起動 / 準備中画面

匿名セッションの復元または自動作成、`public.users.id` 解決、初期設定状態の確認中は、短い準備中画面を表示する。

表示文言は「呼出中・・・」とする。「・・・」のみ静かにアニメーションしてよい。

この画面は通常起動、通知起動、モーニング起動でも違和感がない共通ローディングとして扱う。ただし長く表示せず、起動処理が終わり次第すぐ次画面へ遷移する。

匿名セッション作成や初期化に失敗した場合は通信エラーまたは初期化エラーとして扱い、Google / Apple / emailログインへ誘導しない。

2. 仲良くなれそう
3. 最初から気になる

意味:

- まずは気軽に話したい → 低めの初期親密度
- 仲良くなれそう → 標準の初期親密度
- 最初から気になる → 高めの初期親密度 / 恋愛イベント許可寄り

開始時に `user_characters` の初期行と `character_relationships` の初期行を作成する。実際の数値カラム名・保存値はDB schemaに合わせ、不要なDB構造を増やさない。

# A4. キャラ構成

男女両方を狙う。初期案は女性3人・男性3人程度、合計6人程度。

v1で6人全員か、絞って順次追加かはF章の素材・運用側で決める。

## A4. キャラ構成

人間キャラは男女複数。初期案は女性3人・男性3人程度、合計6人程度。

無料ユーザーはAIを使うメインキャラを1つ選べる。選択肢は人間キャラ1人またはAI猫1匹。

## A5. 関係性・親密度・呼び方

人間キャラは以下を持つ。

- 親密度
- ユーザー側好意度
- 関係状態
- 恋愛イベント許可フラグ

関係状態:

- `friend`
- `close_friend`
- `romance_event_pending`
- `lover`

猫は懐き度と最後に構った時間を持つ。猫は恋愛状態・告白イベントを持たない。

親密度・懐き度の増減は、キャラ側からの通知・モーニングへの反応と、ユーザー発信のチャット・疑似電話・猫への接触の両方で変化する。

AIが自由に点数を決めない。サーバ固定ルールで増減する。LLMは分類や候補抽出に留め、最終判定はサーバ側が行う。

呼び方は関係の到達点として扱う。登録時に必須なのは名前だけ。呼び方の初期指定UIは置かない。呼び方はキャラごとに持ち、関係値で解禁される。

ユーザーが「〇〇と呼んで」と希望しても、関係値/親密度が足りなければキャラが断る。受ける/断る判定はサーバ固定ルール。セリフ生成はLLMでよい。

## A6. 猫仕様

猫は人間キャラと同じ土俵で疑似LINE・疑似電話・モーニングに乗る。違いは人間語を返さない点。

- 猫は恋愛要素なし
- 猫は親密度ではなく懐き度
- ランダム猫はAIなし・無料
- AI猫は感情/反応分類あり・コイン消費
- 疑似LINEでは鳴き声・しぐさテキスト
- 疑似電話/モーニングでは鳴き声音声
- 鳴き声はTTSではなく音声ファイル
- v1ではなで等のタップUIや本格アニメは持たない

## A7. 疑似LINE

疑似LINEは、ユーザーとキャラの基本接点である。通知を開いた後の入口、通話への導線、イベント導線、通話見出しの履歴表示を兼ねる。

疑似LINE履歴は `chat_messages` に保存する。チャット本文と通話見出しは90日で自動削除する。重要なものはピン留めで残せる。

疑似電話後は、疑似LINEに通話見出しを差し込む。通話本文の逐語ログは疑似LINEには入れない。

文字チャットは、AI返信1回ごとの固定コイン消費を基本とする。チャットの文字数上限があるため、入力・出力トークン数による細かな従量計算は行わない。1返信あたりの正式な消費量はF1で決める。固定文言・システム都合の文言・エラー文言は消費しない。

## A8. 疑似電話

疑似電話の入口:

1. ユーザー発信の通話
2. モーニングから会話へ進む通話
3. 日常の気まぐれ着信に応答する通話
4. 特別イベント疑似着信に応答する通話

通常通知は直接通話の入口ではない。疑似LINE画面から通話ボタンで疑似電話へ進む。

iOSの日常の気まぐれ着信は通常APNs通知で知らせる。バックグラウンド・終了中・ロック中は
28.5秒のカスタム通知音を鳴らす。配信から30秒以内の通知タップ後は、同じ音源と反復バイブを
アプリ内疑似着信画面で最大30秒続ける。アプリ前面ではOS通知を重ねず直接疑似着信画面を開く。
PushKit / CallKit / AlarmKit / `ringtoneSoundNamed`は使わない。通知中のバイブ回数と継続は
iOSの通知制御に従い、アプリから29秒の反復を保証しない。AlarmKitはユーザーが登録した
モーニング専用であり、気まぐれ着信には流用しない。

Androidのモーニングはfull-screen intentを使う。日常の気まぐれ着信も通話用full-screen intentを
使うが、通知channel、payload、Activity入口、音の責務はモーニングと分離する。アプリ前面では
OS通知を作らず直接アプリ内全画面疑似着信へ切り替える。前面外では通話カテゴリ通知を出し、
未ロック中はheads-up、全画面通知許可済みのロック中は自動全画面とする。通知上の直接応答・拒否は
使わず、heads-up通知のタップまたはロック中のfull-screen intentからアプリ内着信へ進む。

特別イベント疑似着信は、通常通知 → 疑似LINE → 電話していい？ → OK → アプリ内疑似着信画面 → 応答 → 疑似電話、の流れにする。

日常の気まぐれ着信は、着信を許可したユーザーに対して、着信サイレント時間外だけ
キャラから直接かかる。アプリ前面、バックグラウンド、終了中、ロック中を両OSの対象とする。
応答するまでcall、録音、AI接続、課金、疑似LINEの通話見出しを作らない。拒否・無応答でも
これらを作らず、準備済み接続があれば破棄する。拒否・無応答・第一声準備失敗は対象キャラの
疑似LINEへ不在着信履歴を1件だけ残す。配信候補、端末別配信結果、拒否・無応答・準備失敗という
サーバ内部の運用記録は、頻度制御、診断、重複防止のため保存してよい。

通話開始前に確認するもの:

- 匿名セッション確立済み
- `public.users.id` 解決済み
- 対象キャラ
- マイク権限
- コイン残高
- 通話開始元
- 別通話中でないこと

開始前に最低1課金単位分のコイン残高を確認する。正式な課金単位と開始に必要な最低残高はF1で決める。通話全体の前払いは行わない。

発話中からストリーミング文字起こしを進めるが、AIに渡すのは発話終了が確定した後の確定発話テキストだけ。暫定文字起こしはAIへ渡さず保存しない。

保存するのは確定発話テキスト。

Android実機ではWebViewの `getUserMedia()` に依存しない。

ネイティブ `AudioRecord` で 24kHz / mono / PCM16 を取得して `voice-turn` へ送る。

iOS実機でもWebViewの `getUserMedia()` に依存しない。ネイティブ `AVAudioEngine` で取得したマイク音声を 24kHz / mono / PCM16 へ変換して同じ `voice-turn` へ送り、通話usage・ログ・精算はAndroidと同じOS共通イベントとTypeScript層へ接続する。

AIへ送らないもの。

- 無言
- 咳
- 物音
- 短すぎる音
- 意味のないノイズ
- TTS再生音の回り込み

無音判定時間はユーザーに数値を直接出さず5段階で選ばせる。

- かなり速い = 300ms
- 速い = 400ms
- 標準 = 500ms
- ゆっくり = 700ms
- かなりゆっくり = 900ms

AIには、キャラ基本情報、関係情報、ユーザー理解シート、同日短期文脈、直前LINE/通知文脈、現在の通話内履歴、今回の確定ユーザー発話を渡す。全ログを毎回全文で渡さない。

疑似電話中のAI応答はTTSでキャラ音声再生する。応答テキストは通話中に表示しない。通常応答は1〜3文程度。モーニング由来はさらに短め。

固定文言はAI応答ではなくアプリ側の状態文言であり、その再生時間は課金対象にしない。固定文言にTTSを使っても、AI通常回答でなければ課金対象にしない。

通話は1応答ごとの固定消費ではなく、同じ通話内の次の課金対象時間を合算して計算する。

- 各ユーザーターンの経過時間
- AIの通常回答音声が端末で実際に再生された時間

ユーザーターンは、アプリがそのターンの録音を開始してから、そのターンの終了を確定するまでとする。話し始めるまでの時間、実際に話している時間、話の途中で考えている沈黙、言いよどみ、発話終了判定までの時間、何も話さず無音・聞き取り失敗としてターンが終了するまでの時間を含む。

「無音を課金対象にする」とは、ユーザーターン中の沈黙時間をユーザーターンの経過時間に含めるという意味であり、STT、LLM、TTS、通信などの処理待ちを含める意味ではない。

AI側は、通常回答のキャラ音声が端末で実際に再生された時間だけを含める。再生開始前の時間、生成されたが再生されなかった音声は含めない。途中で再生を止めた場合は、実際に再生された部分だけを対象にする。

呼出中、接続前、WebSocket接続待ち、STT処理待ち、LLM回答生成待ち、TTS生成待ち、音声ファイル取得待ち、通信待ち、再接続待ち、アプリ側の処理遅延、固定の聞き返し音声、エラー案内音声、通話前の固定音声、Good morning onlyの固定音声は課金対象時間に含めない。

内部ではターンごとにユーザーターンの経過時間とAI通常回答音声の実再生時間を記録できる構造とする。通話終了時に同じ`call_id`の記録を合算し、1通話分の消費コインをまとめて確定する。通話中にターンごとに即時減算しない。

アプリ強制終了、異常切断、通信断などでも、保存済みの計測記録から未精算通話を確認・精算できる構造を要件とする。具体的な回収・再試行方法は後続の実装調査で決める。

通話終了時に、少なくとも今回消費したコイン数を確認できる構造にする。課金対象時間の内訳や秒数を利用者へ表示するかはF5で決める。

## A8-2. アプリ内疑似着信の接続と音

アプリ内疑似着信では、応答から会話開始までの待ち時間を最小にする。

- 着信画面の表示中に、通話接続の事前準備(WebSocket接続のstandby確立)を裏で進めてよい。ただし録音・課金・call作成は応答するまで開始しない。
- 拒否した場合、事前準備した接続は破棄し、DBに痕跡を残さない。
- 着信中は着信音を鳴らす。応答または拒否で即座に停止する。
- ユーザー発信の疑似電話では、発信開始から接続確立までコール音(呼び出し音)を鳴らす。
- 接続確立後、キャラの第一声を再生してから会話を開始する。通常のユーザー発信と特別イベント疑似着信では、キャラごとの固定第一声(「もしもし」等)を使う。
- 第一声は毎回のTTS生成ではなく、キャラごとの固定音声とする。固定音声のため課金対象外(AI通常回答音声に含めない)。
- 固定第一声の音声素材の作成・保存は fixed_voice_assets 整備工程で行う。それまでは第一声なしで、接続と音の仕組みのみ先行実装する。
- ただしモーニングの`応答`はA9を優先し、固定第一声を使わない。現在日時、関係性、記憶を踏まえてAIが毎回第一声を生成する。
- 着信音・コール音は生成音声(TTS)を使わず、固定音源または合成音とする。
- 着信音・バイブは端末のマナーモード設定に従う。通常時は着信音+バイブ、マナー(バイブ)時はバイブのみ、サイレント時は無音とする。
- 着信音・コール音の本番音源はF6の音声素材工程で差し替える。
- キャラの発話が終わって録音を再開する前に、短い録音準備音(ピッ音)を鳴らす。この音は課金対象外とし、生成音声(TTS)を使わず合成音とする。
- 録音準備音は、鳴らす／鳴らさないをユーザーが設定画面で選べるようにする。Android・iOSで同じ動きとする。会話が機械的に感じられることを避けたい利用者が消せるようにするため。既定値はF1で決める。

## A8-3. 音声合成(TTS)方式

疑似電話・モーニング等でのAI通常回答のキャラ音声再生は、オンデバイスTTSで行う。

**方式:**

- 端末上のONNX Runtime + Style-Bert-VITS2系AIVMX(各キャラの声モデル)によるオンデバイスTTSだけを採用する。対象はv1の6キャラ全員(H1参照)。桜音1モデルに絞る前提にはしない。
- クラウドTTSは使用せず、クラウドTTSフォールバックも設けない。クラウドTTSの生成・受信・再生・切替分岐を正式実装へ含めない。
- 方式・量子化・配信が実際に成立するかの検証・テストには、桜音(AIVMX)を基準モデルとして用いる。下記の実測基準値も桜音での計測値。
- 理由: TTS従量課金では採算が成立しない。オンデバイス化により、通話・通知の音声再生でTTS変動費が発生しない構造にする。
- `poc/on-device-tts` ブランチでの実験フェーズは終了し、採用を決定済み(2026-07-18)。実験記録は `poc/notes.md` に保持する。

**モデル構成:**

- TTS本体(AIVMX): 動的INT8量子化(MatMul対象・per-channel QInt8)。実機で音質劣化なしを確認済み。主目的はモデルサイズ縮小。
- DeBERTa BERT: 動的INT8量子化。韻律品質維持のため有効のまま使う。BERTスキップ(無効化)は採用しない。
- このうちDeBERTa BERTは全キャラ共通(共有)コンポーネントであり、キャラ別に異なるのはAIVMX(声モデル)・voice-config・ライセンスのみ。
- 量子化・検証はローカルでは行わず、staging AAB workflowのCI内でのみ実行する。

**再生方式:**

- 文末(。!?)単位でストリーミング合成・逐次再生する。1文目の再生開始を早め、体感遅延を短縮する。
- 読点(、)による細分割は、区切りが不自然になるため採用しない。

**声モデルの配信:**

- 声モデルは初期アプリに同梱しない。初回キャラ選択と追加キャラ選択のそれぞれで、選択を確定した時点にCloudflare R2から端末へダウンロードする(egress無料のため)。Android・iOSで同じ動きとする。
- 通話開始を未取得モデルの初回ダウンロード起点にはしない。キャラ選択後、通話を始める前にそのキャラのモデル取得・検証・導入を完了できる導線とする。取得中・失敗時の表示と再試行はキャラ選択導線で扱う。
- 配信は共通BERT bundle(共有DeBERTa BERT＋共通ライセンス。端末へ1回だけDLして保存・再利用)と、キャラ別bundle(AIVMX＋voice-config＋モデルライセンス。キャラごとにDL・保存)に分割する。桜音→別キャラ→桜音のようにキャラを切り替えても、共通BERTと既取得済みキャラモデルは再ダウンロードしない。片方のDL/検証/更新の失敗が既存の正常インストールを壊さない。
- 導入済みbundleはアプリの永続領域へ保存し、通常のアプリ再起動・端末再起動では再ダウンロードしない。bundleの版更新、未取得キャラの選択、アプリ削除後の再インストール等、導入済みbundleを再利用できない場合だけ取得する。
- ライセンス表記文書は声モデルのダウンロード時に同梱・保存する(H1参照)。

**実測基準値(参考):**

- 計測端末: POCO X6 Pro(Dimensity 8300-Ultra)、CPU実行プロバイダ、4スレッド。
- 1文目の再生開始まで約0.9〜1.0秒、RTF約0.7、セッション初期化 約5.5秒(常駐・初回のみ)。
- この端末水準(iPhone 12相当)を、当面の仮の推奨基準端末とする。低速端末対策はF6で決める。

**本実装の要件:**

- 本格実装では、通話フリーズ(応答が返らず固まる)の切り分けのため、STT / LLM / TTS / 再生の各区間ごとにどこで停滞したかを記録するログを含める。

**正式なAndroid通話構成:**

- `AndroidTtfaTestPlugin`は検証用の暫定実装であり、正式実装として残さない。新しい正式Android通話実装へ段階的に置き換え、staging切替と実機確認を終えた後に旧Pluginを丸ごと削除する。
- 新実装は最初から、通話ライフサイクルと状態遷移、WebSocket接続・standby昇格・再接続、録音・VAD・STT送信、オンデバイスTTSのモデル管理・合成・再生、課金usage・終了確定、診断の責務に分割する。
- 正式Android通話実装のTTS経路はオンデバイスTTS専用とする。旧Pluginに存在するクラウドTTSの生成・受信・再生・切替分岐は移植せず、移行完了時に旧Pluginとともに削除する。
- 責務の境界を越えても、モデルsession、AudioTrack、合成・再生executorをturnごとまたは文ごとに不要に再作成しない。通話中に再利用できる資源はライフサイクルを明示して再利用する。
- クラス分割を理由に余計なJSONへの変換・再変換、PCMバッファのコピー、スレッド切替を増やさない。PCMは合成から再生まで不要な複製を避け、既存のproducer / playback consumerの順序保証を維持する。
- 初回音声開始と文間遅延を計測可能にし、機能移行後に実測値を基準として改善する。性能改善のために課金、usage、終了確定、接続状態の正しさを崩さない。

## A9. モーニング

モーニングは、キャラが日常に現れる主要導線。単なるアラームではなく、起床後に疑似電話へ進める入口である。

モーニングはスマホ標準アラームの代替として使えることを前提にする。アプリを閉じている、画面が消えている、
端末がロックされている、または通信できない場合でも、端末へ登録済みのアラームは鳴動できなければならない。
AI通話だけは通信を必要とする。

設定画面は通常のスマホのアラーム一覧と同じ構成にする。

- 複数のアラームを登録できる
- 各アラームに時刻、鳴らす曜日、キャラ、ラベルを設定できる
- 曜日指定の繰り返しと、一回だけの指定日時を扱う
- 一覧のスイッチで個別にON/OFFでき、編集・削除できる
- スヌーズ間隔は1〜60分を1分刻みで選択し、初期値は5分とする
- スヌーズ回数は1回、3回、5回、回数制限なしから選択し、初期値は3回とする
- バイブのON/OFFをアラームごとに選べる
- 音とバイブの両方が無効になる設定は警告し、気付けないアラームを作らない

モーニングの鳴動画面は疑似電話として表現する。アプリ内の操作名と処理は次のとおり。

- `応答`: 鳴動を止め、対象キャラとのAI疑似電話を開始する。ユーザーの発話を待たず、現在日時、関係性、記憶を踏まえてAIが毎回生成した短い第一声をキャラから話す。通話可能なコインがある場合はユーザーデータ全体の読込より先に第一声の文章を先行生成し、応答操作で進行中の準備を破棄しない。通話開始準備と並行しても未完了なら最大0.5秒だけ完成を待ち、それでも未完了または失敗なら応答後に生成する。応答時には最新残高を再確認し、拒否・スヌーズ・未応答では通話履歴とコイン消費を発生させない。固定WAVは使わない。第一声が終わるまで録音せず、終わった後は同じ通話内で通常会話へ進む。AI第一声の実再生時間を含め、通常の通話課金規則を適用する
- `メッセージを再生`: 鳴動を止め、通常と同じ通話画面を表示した直後に近接監視を開始し、1.0秒待ってから、事前に用意した対象キャラの固定モーニング音声だけを再生する。再生準備へ移っても近接監視を維持し、受話口へ近づけた間は画面を消す。待機中に通話を終了した場合は再生しない。再生後も通話画面を維持し、ユーザーの終了操作で閉じる。自動ループと再再生ボタンは設けない。マイクと会話AIは使わず、コインを消費しない
- `拒否`: 鳴動を止め、その日のモーニングを終了する。通話や固定音声は開始しない
- `あとで（○分）`: 鳴動を止め、設定された間隔後に再度鳴らす。設定回数へ達した場合は選べない

内部名`good_morning_only`は互換性のため使用してよいが、画面には「おはようだけ」と表示せず
「メッセージを再生」と表示する。

現在の固定WAVは機能検証用の仮素材である。後続のデザイン・素材工程で、現在より長く、
朝の呼びかけとして内容のある正式文言へ3種類とも差し替える。

iOS 26以上ではAlarmKit導線を使う。CallKit / VoIP pushは使わない。カスタムAlarmKit音やアプリ内Web Audioループ音はv1対象外。

AlarmKitの最初のシステム画面は、停止と、アプリを開くカスタム操作の2つとする。停止はそのまま終了する。
アプリを開くと、AlarmKitの音を鳴らしたまま対象キャラの全画面疑似着信を表示し、上記4操作を出す。
各アプリ内操作はAlarmKitを内部で止めてから後続処理へ進み、別の停止ボタンを要求しない。

Androidはfull-screen intent notificationを使い、同時にOSが許す場合は専用Activityの直接起動も試す。
音はForeground Serviceで鳴らし、全画面表示と分離する。

Androidは最初から対象キャラの全画面疑似着信を表示し、上記4操作を出す。Android 14以降では、
全画面表示の許可をアラーム有効化の必須条件とする。未許可の場合は端末の許可画面を開き、許可後の
再保存を求める。許可が無い状態をアラーム設定完了として扱わない。
全画面疑似着信は通常アプリ画面とは別の専用タスクで開く。専用Activityが既に存在していても、
新しいアラームのIntentを必ず取り込み、以前表示していた設定画面等を着信画面として再利用しない。
継続通知の`応答`は対象アラームの応答としてAI通話を直接開始し、通知本文のタップは全画面疑似着信を開く。

OSまたはメーカー制限によりfull-screen intentも直接起動も拒否された場合は、音を鳴らしたまま
継続通知を出す。通知には`応答`と`停止`を表示し、`応答`または通知本体から同じ疑似着信Activityへ入れる。

応答後はMainActivityへ飛ばさない。

ロック解除を前提にした通常アプリ起動ではなく、ロック画面上の専用Activity内でAI通話接続状態へ進める。

AndroidはConnectionService / Telecomを使わない。

モーニングはアラーム系導線として、full-screen intent + Foreground Service + アプリ内疑似通話Activityで構成する。

`応答`と`メッセージを再生`のどちらも、終了後は疑似LINEへ通常と同じ「通話」見出しを残す。
表示上の履歴種別や文言は分けない。

## A8-4. Good morning only

Good morning only は画面上では「メッセージを再生」と表示する。事前に用意した固定音声のみで消費なし。

v1ではキャラごとに3種類の固定モーニング音声を用意する。前回再生した音声を端末内に記録し、
候補が複数ある場合は直前と同じ音声を避けて選ぶ。関係性ごとの増加はv1に含めない。

固定音声は初回・追加のキャラ選択時に、そのキャラの会話用TTSモデルと一緒に端末へ保存する。
モーニング設定・同期時は保存済み音声を確認し、不足または更新分だけを取得する。鳴動時の
「メッセージを再生」は保存済みの音声だけをローカル再生し、LLM、会話用WebSocket、
マイク、コイン消費を使わない。通常と同じ通話画面と「通話」見出しを残すためのcall記録だけは作成する。
音声が未保存の場合は会話AIや端末標準TTSへ
置き換えず、準備中として明示する。会話用TTSモデルが配信されていないキャラは、
選択後に無音となるため選択可能に表示しない。

`応答`で疑似電話へ進んだ後は、AIが生成した第一声を含む通常回答音声の実再生時間と、
その後のユーザーターンの経過時間を合算する通常の通話課金ルールを適用する。

## A9-1. 会話からのモーニング登録

設定画面に加え、キャラとのチャットまたは通話でモーニング登録を依頼できる。

- 「明日7時に起こして」は一回だけの候補にする
- 「毎週月曜から金曜の7時に起こして」は曜日指定の繰り返し候補にする
- 会話AIはアラームを直接登録しない
- 日付、曜日、時刻、繰り返し、キャラを明示した確認を疑似LINEへ出す
- ユーザーが「設定する」を選んだ場合だけ端末とDBへ登録する
- 曖昧な日時は登録候補にせず、キャラが聞き返す
- 通話中の依頼では、キャラが「通話後に確認を送るので、そこで設定して」と音声で伝える
- 通話終了後、同じ確認を疑似LINEへ出す。未確認、拒否、期限切れの候補は鳴らさない

# A9. 通知

## A10. 通知

v1で扱う通知:

- モーニングコール
- デイリー生成通知
- 気まぐれ通知
- イベント通知

モーニングは通常通知とは別枠。デイリー通知とキャラ側からの着信は、A10-2の共通スケジューラが
一つの枠として割り当てる。デイリー枠は1日1回で、その中身は通知または着信のどちらかになる。
気まぐれは通知と着信に分けず、デイリー枠とは別の一つの枠として扱う。
デイリー枠を毎日1回割り当てる原則は、休眠が続く場合と、利用者が設定で連絡の量を少なめにした
場合に例外を持つ（A10-2・B4）。

通知タップ後の疑似LINE画面には、キャラからの入口メッセージを置く。通常通知では
入口メッセージを唯一の本文とし、通知用の別文面を生成しない。

- 入口メッセージは通知生成時に事前生成して保存する
- デイリー通知は通話開始前のテキストメッセージとし、「もしもし」「聞こえてる？」「電話」「通話」など既に音声通話中であるような本文・話題は候補に保存しない
- ロック画面へ出して安全な入口メッセージは、同じ全文を通知本文にも使う
- 「トーク内容を表示しない」がON、または安全検査に通らない場合だけ、通知本文を「{キャラ名}からメッセージが届いています」へ置き換える
- アプリ前面で同じキャラのトークを表示中は通知UIを出さず、入口メッセージだけを一度反映する
- 別キャラのトーク、ホーム、設定などを表示中は現在画面へ内容を重ねず、OS通知を出す
- アプリがバックグラウンド、画面ロック中、終了中なら、最後に開いていた画面に関係なくOS通知を出す
- 入口メッセージと通知結果の保存先は `notification_candidates`
- 実配信が受理された時点で `notification_logs` を作り、`candidate_id`で生成候補へつなげる。未配信候補のログは作らない
- モーニングは入口メッセージの対象外

通常メッセージ通知と、キャラ側から自発的に始める疑似着信は独立してON/OFFできる。
通知ON・自発的着信OFFを許容する。自発的着信OFFはOS通知許可や通常メッセージ通知を
無効化しない。ユーザーが明示登録したモーニングは各アラームのON/OFFを正とし、
自発的着信OFFには連動させない。

通常メッセージ通知のサイレント開始・終了と、自発的な疑似着信のサイレント開始・終了は
別々に設定できる。通知だけ受けて着信を止める時間帯、またはその逆を許容する。
登録済みのモーニングは、どちらのサイレント時間にも連動させない。

## A9-2. デイリー / 気まぐれ / lover通知

通知が送られる条件:

- 通知全体ON
- そのキャラの個別通知ON
- サイレント時間帯外
- 枠の割り当てあり
- 有効な端末通知トークンがある

製品上は1ユーザーにつき有効端末を1台だけとする。通知送信時は `device_installations` の有効端末1台へ送る。引き継ぎ完了時に新端末を有効化し、旧端末のPush token、着信、通知、モーニングを無効化する。同一ユーザーの複数端末同時利用と端末間の先着応答はv1対象外とする。

デイリー通知のキャラ枠:

- `lover`が1人以上いる場合は、通知ONのlover全員を毎日の対象にする
- `lover`がいる場合も、それとは別に、通知ONの非loverから関係値重み付きで1人を日替わりで追加する
- `lover`がいない場合は、通知ONのAIキャラから関係値重み付きで1人を日替わり選択する
- 各対象の枠は1日1回で、その中身は通知または着信のどちらかになる。振分はA10-2による
- 選択はユーザー・現地日付・キャラIDから再現可能にし、同日再試行で対象が変わらない
- 関係値重みの正式数値はF3で決定し、それまでは交換可能な暫定式を使う
- 割当と配信は分離し、配信直前にも設定、quiet hours、端末状態を再確認する

## A10-1. 日常の気まぐれ着信

日常の気まぐれ着信は、イベント・告白とは無関係な、キャラからの日常的な直接着信である。

- `settings.incoming_call_enabled = true` の場合だけ候補にできる
- `incoming_call_quiet_hours_start/end` の時間帯には配信しない
- ユーザーが登録したモーニングの前後や、通常通知・別の着信と近接させない
- 日・週単位の上限を持ち、拒否・無応答を頻度調整へ使える構造にする
- 通知と着信の候補時刻、頻度、対象キャラは一つの共通スケジューラで決める。内容はA10-2とする
- 最初の運用では通知だけを実配信し、着信候補を記録だけするdry-runを可能にする
- 残高が共通スケジューラで決める基準未満なら着信候補を作らず、必要に応じて通常メッセージ候補へ振り分ける。応答時にも最新残高を再確認する
- 候補作成時に日時・関係性・記憶を使った短い第一声テキストを生成し、成功した候補だけ配信する
- Androidはアプリ前面ではhigh-priority FCM受信後に第一声PCMを準備し、完了時にアプリ内全画面疑似着信・着信音・バイブ・有効な応答ボタンを同時に開始する。準備中は受信前の画面を維持する
- Androidはアプリ前面外で30秒の通話カテゴリ通知へfull-screen intentを付ける。端末ロック中かつ全画面通知許可済みなら自動で全画面疑似着信を表示し、未ロックでホーム画面または他アプリを表示中はheads-up着信通知を表示して、タップ後に全画面疑似着信へ進む
- Android 14以降では、新規初期設定、既存ユーザーの着信設定有効時の初回起動、着信設定ON時に、通常通知許可の後で`全画面通知を許可`設定を開き、アプリ復帰後に許可状態を再確認する。全画面通知が未許可なら着信設定完了扱いにせず、実着信時はheads-up通知へ縮退する
- iOSのバックグラウンド・終了中・ロック中は、同梱した28.5秒WAVを指定した通常APNs alertを受ける
- 前面外の通知表示はタイトル`{キャラ名}から着信`、本文`着信中`とする。内容非表示設定時はキャラ名を出さず、タイトル`着信`とする
- 自動全画面にならない状態では、配信開始から30秒以内の通知タップで対象通知を消し、着信音と反復バイブを伴うアプリ内全画面疑似着信へ進む
- iOSの前面受信はOS通知を重ねず、直接アプリ内全画面疑似着信へ進む
- iOSの通知中のバイブはOS制御であり、アプリが29秒の反復を保証する要件にはしない
- 通知を開いた時点から全画面着信の30秒を開始する。全画面中にアプリを閉じる、バックグラウンドへ戻す、拒否する、30秒無操作のいずれでも着信を終了する
- 通知を配信から30秒無視した場合と全画面着信を終了した場合は、対象キャラのトークへ`{キャラ名}からの不在着信`を時刻付きで1件だけ残す
- 期限後の通知タップは全画面着信やAI通話を開始せず、対象キャラのトークを不在着信位置で開き、配信済み通知を削除する
- Androidのアプリ前面受信だけは、保存済み第一声のPCM準備完了まで受信前の画面を維持し、準備完了時に全画面着信・着信音・バイブ・有効な応答ボタンを同時に開始する。前面外とiOSは従来どおり全画面着信と着信音を直ちに開始し、同じ全画面内でPCMを準備する。別のローディング画面は設けない
- 第一声の準備中は拒否を常に操作可能にし、応答ボタンだけを無効化してスピナーと`準備中…`を表示する。準備完了時に`応答`へ切り替える。準備前に押した応答を予約して、完了後に自動応答する挙動は採用しない
- Androidは応答後に1.0秒の受話猶予を置いてから第一声の通話接続を開始する。第一声終了後は通常回答と同じ録音準備音（ピッ音）を鳴らし、再生完了・準備音完了・次turn standby readyの到着順にかかわらず必ず録音可能な次ターンへ進む。第一声の実再生時間だけ通常課金規則を適用する。録音準備音のON/OFF設定は後工程とする
- 第一声テキスト生成失敗時は通知を送らない。オンデバイスTTS準備は一度再試行し、それでも失敗した場合は応答、call作成、録音、課金を行わず不在着信にする
- iOSの気まぐれ着信にPushKit、CallKit、AlarmKit、`ringtoneSoundNamed`を使わない
- Androidのモーニング用Alarm Service、iOSのAlarmKitへ気まぐれ着信を混在させない
- 応答後は両OSとも`spontaneous`を発信元として既存のOS共通通話開始処理へ合流する
- candidate IDと有効端末1台を照合し、期限切れ、重複配信、別ユーザーの応答を拒否する

## A10-2. 通知・着信の共通スケジューラ

デイリー枠と気まぐれ枠について、対象キャラ、通知か着信かの振分、配信時刻を一つのスケジューラで
決める。通知だけ、着信だけを別々に割り当てる形にはしない。

**枠の構造:**

- デイリー枠は1日1回とし、中身は通知または着信のどちらかにする
- 気まぐれ枠はデイリー枠とは別に持ち、中身は同じく通知または着信のどちらかにする
- 気まぐれは日・週の上限を保険として持つが、上限まで使い切る形にはせず毎日抽選で発生させる。
  上限を毎回使う運用は回数が規則的になり、人からの連絡として不自然になるため採用しない
- 1日に成立する着信は最大1回とする。デイリー枠と気まぐれ枠のどちらが先でも、先に着信が入った
  側を着信とし、もう一方はその日は通知にする

**対象キャラ:**

- デイリー枠の対象はA9-2による
- 気まぐれ枠の相手は、通知ONの全キャラから関係の深さの重みで1人選ぶ
- 同じ日にデイリー枠で接触したキャラは気まぐれの重みを下げるが、除外はしない。loverは毎日
  デイリー枠の対象になるため、除外するとloverから気まぐれが永久に来なくなる
- この結果、loverとは1日2回やりとりする日が出る。これは許容する

**通知か着信かの振分:**

- 関係が深いほど着信になる割合を上げる
- 着信設定がOFFなら、その枠は最初から通知にする
- 着信サイレント時間帯は、最初から時刻の候補に入れない。生成後に弾く形にはしない
- 残高がスケジューラで決める基準未満なら通知にする
- 購入・サブスクの`coin_lots`を持たない無料のみのユーザーは、着信になる割合を下げる。ゼロには
  しない。着信を一度も体験しないまま離脱すると、課金の動機そのものが生まれないため
- 休眠中は着信にせず通知だけにする

**配信時刻:**

- 固定時刻には配信しない。起きている時間帯の中から時刻を抽選して散らす
- 着信サイレント時間帯を設定していないユーザーにも既定の夜間帯を適用し、夜間には配信しない。
  未設定を理由に深夜へ配信しない
- ユーザーが自分から通話またはチャットで接触したキャラは、そのキャラからの配信時刻を後ろへ
  ずらす。ずらした先が配信可能な時間帯に収まらない場合は、その日は配信しない
- 近接回避の間隔は、同じキャラからの連絡と別キャラからの連絡で別々に持つ。同じキャラは長く、
  別キャラは短くてよい
- 同じキャラで間隔を確保できない場合は、気まぐれ枠を送らない。デイリー枠を優先する
- ユーザーが登録したモーニングの前後には配信しない

**休眠時の減衰:**

- 最終利用からの日数に応じてデイリー枠の頻度を落とす。完全には止めない。呼び戻しの機会を残す
- アプリを開いた時点で通常の頻度へ戻す
- 休眠中は着信にせず通知だけにする。無料コインが毎日回復するため、残高では休眠ユーザーへの
  着信を止められない

**利用者による頻度設定:**

- 設定画面で連絡の量を3段階から選べるようにする
- この設定が動かすのは連絡の量だけとし、着信になるか通知になるかは変えない。着信が不要な
  利用者は着信設定をOFFにできるため
- 少なめではデイリー枠も毎日ではなくなり、気まぐれも減る。気まぐれをゼロにはしない

**F3 v2正式値:**

- 少なめ: デイリー50%＋気まぐれ基準7%
- ふつう: デイリー100%＋気まぐれ基準15%（既定値）
- 多め: デイリー100%＋気まぐれ基準45%
- 気まぐれの実発生率は、先に関係値重みで相手を1人抽選し、そのキャラの基準率へ
  `0.75 + intimacy_score×0.005`（親密度は0〜100へ丸め、倍率0.75〜1.25）を掛ける。
  親密度0／50／100なら、ふつうの気まぐれ率は11.25%／15%／18.75%となる。所有キャラが
  1人だけでもこの補正は有効とし、関係が深くなるほど少しずつ発生率が上がる
- 気まぐれ上限は1日1回・週3回。着信は全枠を合わせて1日最大1回
- 同一キャラは6時間、別キャラは90分、利用者からの連絡後は3時間、モーニング前後は90分空ける
- 配信可能時間は現地8:00〜21:59。7日休眠でデイリー発生率を45%、30日休眠で20%へ減らし、休眠中は通知だけにする
- 着信最低残高は3。無料のみの利用者は関係値から求めた着信率へ45%を掛ける
- キャラ選択の関係値重みは`1 + intimacy_score÷20`（親密度は0〜100へ丸める）。整数段階へ
  切り捨てず、親密度1点ごとに連続して変える。複数キャラでは関係が深いキャラほど当選しやすく、
  同日デイリー相手の気まぐれ重みは35%へ下げる
- 着信率は基礎8%にlover 18%／close_friend 10%、affinity_level 1段階ごと5.5%、intimacy_score÷600（最大18%）を加え、全体上限72%とする

## A11. イベント・告白

イベントは、親密度が上がったから発生するキャラ側からの変化。通知、疑似LINE、疑似電話を組み合わせる。

告白の基本パターン:

1. イベント通知
2. 疑似LINEに入口メッセージ
3. キャラが「少し電話してもいい？」
4. ユーザーがOK
5. アプリ内疑似着信画面
6. 応答
7. 告白用の短い疑似電話
8. ユーザー選択
9. 結果反映

最初から着信ではない。ユーザーがOKした後で疑似着信にする。

## A10-5. 告白の返答

選択肢。

- OK
- 断る
- まだ早い
- 友達でいたい

OK以外はloverにしない。

告白・関係変化・呼び方変更・強めのイベントは、ユーザーの明示同意を挟む。

- 告白: OK / 断る / まだ早い
- 関係状態変更: OK / 今のまま / 戻す
- 呼び方: OK / 今はやめる
- キャラが勝手に変更しない。同意前は `pending`
- 既読だけ・放置は同意ではない
- 未応答なら状態を戻す、または保留する
- しつこく迫らない

## A10-6. lover後

告白OKで関係状態 `lover`。

loverは通知上も会話上も文脈が変わる。

lover後の過去イベントはrememberableにする。

口調・態度・通知の温度・疑似電話やモーニングの一言は、関係状態を `lover` としてLLM文脈に渡すことで自動的に恋人トーンになる。

無料ユーザーでもlover化可能。恋人化を有料限定にしない。

AI会話継続は通常どおりコイン消費。

## A10-7. 告白の課金

告白の最初の固定一言はコイン消費しない。

本題以降にAI生成へ進む場合、通常どおりコイン消費。

告白イベントの最初の本題1往復を無料または固定音声に寄せるかはF章で決める。

# A11. 安全・コンテンツ方針

## A11-1. 基本路線

健全路線。性的表現・過激表現は禁止。

告白OKで関係状態 `lover`。lover後の過去イベントはrememberableにする。

無料ユーザーでもlover化可能。恋人化を有料限定にしない。AI会話継続は通常どおりコイン消費。

## A12. 安全・コンテンツ方針

健全路線。性的表現・過激表現は禁止。恋愛は情緒的・日常的な範囲まで。

禁止:

- 性的描写 / 性行為 / 露骨な誘惑
- 未成年との恋愛・性的文脈
- 自傷・他害の助長
- 違法行為の助長
- 現実の人物へのなりすまし
- 依存を強める過度な束縛・罪悪感誘導

通知文にセンシティブ情報を出さない。恋愛関係でも、ロック画面通知で過度に親密・恥ずかしい文言を出さない。

自傷・他害・医療・法的相談などはキャラ人格より安全テンプレートを優先する。緊急時は公的窓口・地域別ヘルプに誘導する。

# B. 課金設計

## B1. 通貨単位

アプリ内通貨はコイン。ユーザー向け表示はコインで統一する。

## B2. 消費しないもの

- デイリー通知のAI生成
- 通知文
- 入口メッセージ
- 固定・テンプレ通知
- モーニングのAlarmKit音
- Good morning onlyの固定音声
- 通話前の最初の固定一言
- 特別イベント最初の固定一言
- 聞き取り失敗・無音・雑音の固定文言
- ランダム猫のAI不使用反応
- 日次処理の要約・分類
- エラー文言

通話では、次の待ち時間・固定音声の再生時間を課金対象時間へ含めない。

- 呼出中・接続前
- WebSocket接続待ち・通信待ち・再接続待ち
- STT処理待ち・LLM回答生成待ち・TTS生成待ち
- 音声ファイル取得待ち・アプリ側の処理遅延
- 固定の聞き返し音声・エラー案内音声の再生時間
- 通話前の固定音声・Good morning onlyの固定音声の再生時間

無音・聞き取り失敗として確定するまでのユーザーターン経過時間は課金対象である。その後に流れる固定の聞き返し音声の再生時間は課金対象外であり、両者を混同しない。

## B3. 消費するもの

- 文字チャットでAIが返答した時の、AI返信1回ごとの固定消費
- 通話中の各ユーザーターンの経過時間
- 通話中のAI通常回答音声が端末で実際に再生された時間
- AI猫がユーザー入力に対して感情分類して鳴き声反応を返す時

チャットは文字数上限を前提とし、入力・出力トークン数による細かな従量計算は行わない。通話は1応答ごとの固定消費にせず、ターンごとに記録した課金対象時間を通話終了時に合算し、1通話分を一括精算する。

固定文言はLLMを呼ばないので消費しない。固定文言にTTSを使っても、AI通常回答でなければ再生時間を加算しない。TTS生成失敗・再生失敗、および生成されたが再生されなかったAI音声は課金対象にしない。

## B4. 無料ユーザー

無料ユーザーに提供するもの:

- 1AIメインキャラ
- ランダム猫
- モーニング導線
- デイリー通知（原則1日1通。休眠が続く場合と、利用者が設定で連絡の量を少なめにした場合は毎日でなくなる。A10-2参照）
- 関係進行 / 告白イベント
- 毎日回復コイン

関係値進行や告白は有料限定にしない。AI会話量は無料回復コイン範囲に制限される。

## B5. 月額会員 / 定期コイン

サブスクは無制限ではなく、割安な定期コイン付与。

- 月額で一定数コインを付与
- 未使用コインの繰り越し上限を持つ
- サブスク限定で追加キャラ枠・通知上限・一部イベント演出を優遇する余地を残す

## B6. キャラ枠課金

AI利用キャラ枠は1枠=1キャラ固定。入れ替え制ではない。

- 無料ユーザーはAI利用可能なメインキャラを1つだけ選ぶ
- 別キャラでもAIを使いたい場合は追加AI利用キャラ枠を購入
- 追加枠は購入時にキャラを1人固定で割り当てる
- 後から別キャラへ入れ替える仕様にはしない
- ランダム猫はAIを使わないので無料付属・枠消費なし
- AI猫はAIを使うため、人間キャラと同じくAI利用キャラ枠を消費する

## B7. RevenueCat app user id

RevenueCat app user id は `public.users.id` とする。

使わないもの:

- `auth.users.id`
- 端末ID
- GoogleアカウントID
- AppleアカウントID
- email

Supabase Auth anonymous session の `auth.users.id` は認証セッションIDであり、RevenueCat app user idには使わない。

RevenueCat購入確認・Webhook・復元処理は、最終的に `public.users.id` に対してコイン付与・キャラ枠付与を行う。

## B8. 購入復元

購入復元はRevenueCatで確認する。ただし、アプリ内データの復元は `public.users.id` に戻れるかどうかに依存する。

原則:

- 引き継ぎコードがある場合、旧 `public.users.id` に戻す
- その後、RevenueCat app user id も同じ `public.users.id` で扱う
- 引き継ぎコードなしで再インストールした場合、新しい `public.users.id` が作られる
- その場合、購入状態はRevenueCat上で確認できても、旧キャラ記憶・関係値・チャット履歴・コイン残高は原則戻らない

消耗型コインは、復元で再付与しない。RevenueCatイベントID・store_transaction_id・idempotency_keyで二重付与を防ぐ。

非消耗キャラ枠・サブスクentitlementを現在の `public.users.id` へ自動反映するか、サポート確認にするかはF章で実装条件を決める。

## B9. 引き継ぎ失敗時の扱い

引き継ぎ失敗例:

- コード期限切れ
- コード使用済み
- 入力ミス
- 旧端末が手元にない
- RevenueCatでは購入済みだが、旧 `public.users.id` に戻れない

方針:

- 引き継ぎコードなしでは、旧キャラ記憶・関係値・チャット履歴・コイン残高は原則戻せない
- 購入済みの非消耗枠・サブスクはRevenueCatで確認し、現在の `public.users.id` に反映する余地を残す
- 消耗型コインは二重付与防止を優先する
- ユーザーに「引き継ぎコードなしでは会話履歴や記憶は戻せない」ことを明示する

# C. アカウント・引き継ぎ設計

## C1. 基本方針

ログイン画面を作らない。

初回起動時にSupabase Auth anonymous sessionを自動作成する。

アプリ内ユーザー主キーは `public.users.id`。

`auth.users.id` は `public.users.auth_user_id` にだけ紐づける。

## C2. 匿名セッション / Supabase client制約

起動時に既存セッションがなければ `signInAnonymously()` を実行する。

Supabase local config と本番Dashboardの両方で Anonymous sign-ins を有効化する必要がある。

匿名セッション作成に失敗した場合は、初期化エラーとして扱う。ログイン画面へ逃がさない。

Supabase client初期化時、env未設定なら空文字で初期化しない。明示的にErrorを出す。

`onAuthStateChange` 内ではDB queryを直接awaitしない。セッション状態を更新した後、別非同期処理で `public.users.id` 解決とユーザーデータロードを行う。

古いload結果で新しいセッション状態を上書きしない。load sequence等で最新の読み込みだけを反映する。

# C3. `auth.users.id` と `public.users.id`

`auth.users.id` は認証セッションID。

`public.users.id` はアプリ内ユーザーID。

解決経路:

```text
Auth session
  auth.users.id
    ↓ user_auth_links.auth_user_id または public.users.auth_user_id
  public.users.id
    ↓
  settings / coin_balances / user_characters / chat_messages / calls / user_character_memory / revenuecat_events / coin_transactions / coin_lots / coin_consumptions
```

各ユーザー別テーブルの `user_id` は `public.users.id` を参照する。

アプリ側にはservice role keyを置かない。

アプリ側はanon / publishable key + RLS前提で動かす。

service role相当の権限が必要な処理は、Edge Functionまたはsecurity-definer RPCへ閉じる。

# C4. 初回ユーザー作成

Authユーザー作成時triggerまたは初回データロードで自動作成するもの:

- `public.users`
- `public.settings`
- `public.coin_balances`

自動作成しないもの:

- `notification_preferences`
- `user_characters`
- `character_relationships`
- `user_character_memory`
- `device_installations`

これらは初回オンボーディングや端末登録時に作成する。

## C5. 端末インストール管理

`device_installations` を持つ。

目的:

- push token管理
- 端末別通知許可状態
- 同一ユーザーの複数端末管理
- 引き継ぎ後の二重通知防止
- 退会時の端末無効化

同じ `public.users.id` に複数端末が紐づく可能性を許容する。

## C6. 引き継ぎコード発行

旧端末で引き継ぎコードを発行する。

- 生コードはDBに保存しない
- DBには `code_hash` のみ保存
- 有効期限を持つ
- 単回使用
- 発行者の `auth.users.id` を保存
- 対象の `public.users.id` を保存
- 発行処理はEdge Functionまたはsecurity-definer RPC経由
- クライアントが `transfer_codes` を直接insert/select/updateしない

## C7. 引き継ぎコード入力

新端末で引き継ぎコードを入力する。

流れ:

1. 新端末で匿名セッション作成
2. 新しい仮 `public.users.id` が作成される
3. 引き継ぎコード入力
4. サーバ側でコード照合
5. 有効期限・使用済み・ハッシュ一致を確認
6. 旧 `public.users.id` に戻す
7. 新端末の `auth.users.id` を旧 `public.users.id` と紐づける
8. 仮ユーザーを無効化または削除候補にする

RLS上の現在ユーザー解決は、原則 `user_auth_links.auth_user_id = auth.uid()` かつ `is_current = true` を使う。

`users.auth_user_id` は現在代表リンクのキャッシュまたは単一現行セッション用の互換カラムとして扱う。矛盾時は `user_auth_links` を正とする。

引き継ぎ完了時は旧端末リンクを `is_current = false` にする。複数端末を許す場合でも、通知対象は `device_installations` で制御し、RLSのユーザー解決と通知送信先を混同しない。

## C8. 再インストール時

引き継ぎコードなしで再インストールした場合、新しい匿名ユーザーになる。

旧チャット履歴・記憶・関係値・コイン残高は原則戻せない。

購入状態はRevenueCatで確認できる場合があるが、アプリ内データ復元とは別問題。

## C9. 退会・削除

- 会話
- 記憶
- 行動ログ
- 通知候補
- 端末トークン
- キャラ関係状態

保持または匿名化するもの:

- 購入ログ
- RevenueCatイベントログ

# D. DB設計

## D0. DB全体方針

`public.users.id` がアプリ内user_id。

`public.users.auth_user_id` が `auth.users(id)` を参照する。

他テーブルの `user_id` は `auth.users(id)` ではなく `public.users(id)` を参照する。

古いmigrationに `relationships.user_id references auth.users(id)` のような記述が残っている場合は、v4方針と衝突するため整理対象。

RLSは `auth.uid()` から `public.users.id` を解決して判定する。

RLS上の現在ユーザー解決は、`user_auth_links.auth_user_id = auth.uid()` かつ `is_current = true` を正とする。

`users.auth_user_id` は、現在の代表リンクを参照するキャッシュまたは互換カラムとして扱う。

`users.auth_user_id` と `user_auth_links` が矛盾した場合は、`user_auth_links` を正とする。

引き継ぎ時は新しい `auth_user_id` のリンクをcurrent化し、旧リンクは必要に応じて `is_current = false` にする。

# E. 記憶設計

## E1. 4層の記憶

1. 画面履歴

- チャット本文
- 通話見出し
- 90日で自動削除
- 重要なものはピン留めで残せる

2. 夜間処理後の未整理文脈

- 最後に成功した夜間処理より後のチャットログ
- 通話終了後に作った正式な通話要約
- 現在の通話内の直近履歴
- 同日短期文脈専用テーブルは作らない
- チャットは通常すべて渡し、最大20,000文字。超過時は新しい会話を優先する
- 未整理の通話要約は1本最大1,000文字、合計最大5,000文字

3. 日次要約

- ユーザー×キャラ×日付ごとに夜間処理で作る
- その日の会話の流れを400〜800文字、最大1,000文字へまとめる
- 直近7日分をAIへ渡す
- 作成から7日で削除する
- 会話が無かった日は作らない

4. 長期記憶

- キャラが長期間覚える必要がある、特に重要な要点・状態
- `user_character_memory` に保存
- 恒久保存

長期記憶例:

- 呼び方
- 好き嫌い
- 生活リズム
- 重要イベント
- 関係状態
- 禁止事項
- 安全フラグ

## E2. 通話ログ保存

通話中は `call_logs` に確定テキストとAI応答テキストを保存する。

音声ファイル保存は必須ではない。

課金・誤課金防止のため、各ターンの録音開始から終了確定までの経過時間と、AI通常回答音声の実再生時間を保存する。固定の聞き返し音声・エラー案内音声の再生時間はAI通常回答音声の実再生時間へ含めない。

通話終了時に同じ`call_id`の保存済み計測記録を合算して一括精算する。強制終了・異常切断・通信断で終了処理が完了しなくても、未精算通話を確認して回収・再試行でき、二重精算しない構造にする。

通話終了後、保存済み全文から正式な`call_summaries`を非同期生成する。要約生成をユーザーに
待たせない。次のチャット・通話は、日次要約へ未反映の正式な通話要約を文脈へ加える。

同じ通話が長くなり、現在の通話内履歴が10往復または12,000文字へ近づいた場合は、古い部分
だけを通話中の一時要約へまとめ、最近の会話は原文のまま残す。一時要約はその通話内だけで使い、
通話終了時に破棄する。正式な通話要約は一時要約からではなく保存済み全文から作る。

夜間処理成功後に `daily_summaries` / `user_character_memory` へ反映し、処理済み`call_logs`の
本文を削除する。正式な通話要約、未処理の通話本文、日次要約はいずれも作成から最大7日保持する。
処理失敗中の通話本文は翌日へ繰り越すが、7日を超えて本文を保持しない。

## E3. 日次処理

対象:

- その日の日次処理ウィンドウ内のchat_messages
- call_logs
- 通話終了後に生成済みのcall_summaries
- event_states
- notification_logs

通話がどの日のものかは終了時刻で決める。開始時刻は使わない。疑似LINEの通話見出しが終了時刻の位置へ差し込まれるため、画面上の並びと日次処理の帰属を一致させる。日付をまたいだ通話も分割せず、終了時刻の日へまとめて入れる。

処理単位はユーザー×キャラ×日付とする。同じユーザーでもキャラごとに入力・出力を分離し、
別キャラとの会話や記憶を混ぜない。会話量がモデル入力上限を超える場合だけ分割する。

日次処理は既存の毎晩の自動実行へ相乗りし、日本時間03:30の異常通話回収後に開始する。
一時的な通信失敗、タイムアウト、AIサービス側エラーは、失敗した処理単位だけ同日04:00と
05:00に再試行する。入力不正など再試行不能な失敗は同日に繰り返さない。2回の再試行でも
失敗した処理単位は元の日付を維持して翌日へ繰り越し、別の日付の処理を止めない。

出力:

- daily_summaries
- user_character_memoryの更新
- relationship/intimacy補正候補
- 翌日以降の通知材料

日次処理でやらない:

- 次の日の通知文を全部確定
- 長期記憶の間引き
- 自動のキャラ関係変化確定
- 自動恋人化

## E4. AIに渡す文脈

毎回固定で渡す:

- キャラpersona
- 関係状態
- 呼び方
- 長期記憶（ユーザー理解シート5種類すべて）
- 直近7日分の日次要約
- 現在日時(日付・曜日・時刻)

現在日時はユーザーの`settings.timezone`で解決した現地時刻を渡す。サーバー時刻をそのまま渡さない。時刻を渡すのは、朝・昼・深夜で会話の内容が変わるためである。通話中はターンごとに更新し、日付をまたぐ長時間通話でもずれないようにする。

「明日」「先週」のような相対表現はそのまま保存しない。記録時に絶対日付へ変換する。相対表現のまま長期記憶へ入れると、読むたびに解釈が変わり、毎日「明日プレゼンがある」と言い続けるような破綻が起きる。

状況で渡す:

- 最後に成功した夜間処理より後のチャットログ（最大20,000文字）
- 日次要約へ未反映の正式な通話要約（1本最大1,000文字、合計最大5,000文字）
- 通知/イベント文脈
- 今の通話内の直近履歴
- 長い通話で作った、その通話内だけの一時要約
- 関係変化/告白pending状態

渡さない:

- 全履歴全文
- 古いログ全部
- 不要なセンシティブ情報

## E5. 長期記憶更新

AIに自由に記憶を決めさせない。

AIは候補抽出・分類だけ。

サーバ側ルールで採用/不採用を決める。

採用ルール:

- 好み・出来事は1回の言及で採用する。
- プロフィール(仕事・家族・住まい)は2回言及されてから採用する。誤って覚えたときに会話が壊れる度合いが大きいため。
- 「その話はやめて」に類する要求は1回で即採用し、自動では消さない。嫌なことを2回言わせない。
- ユーザーによる明確な否定は、種類を問わず1回で反映する。

既存の記憶と食い違う発言があったときの扱い:

- 好み・趣味・持ち物など本人が話しやすい話題は、会話で確認してよい。確認は1日1件までとする。取り調べのように繰り返さない。
- 家族・健康・仕事を失う話・住まいの変化は確認しない。黙って新しい内容へ更新する。失った話を確認で掘り返さない。
- 確認して答えが得られない場合は両方を残して「未確定」とし、AI側からその話題を持ち出さない。
- ユーザーが自分からその話題を出した場合は、触れられた側だけを確定にする。もう一方は未確定のまま残す。
- 記憶を消すのは、ユーザーがはっきり否定したときだけとする。

ユーザーに見せる/消す機能はv1では最小。v2で詳細管理。

# H. 検証済み前提

## H1. 声モデル

AivisHub上で商用利用可能なACML 1.0モデルを確認済み。アプリへの組み込み・再配布が可能であることを確認済み(桜音モデルで確認)。

利用条件:

- 声モデルの配布(ダウンロード)にライセンス文書を同梱する。
- 非公式かつ本人(声の提供元)とは無関係である旨を表記する。

v1仮採用:

- 女性: まお / コハク / 桜音
- 男性: にせ / fumifumi / 猩々博士

オンデバイスTTSは上記6キャラ全員に適用する。桜音1モデルに絞る前提にはしない。方式・量子化(動的INT8)・配信(Cloudflare R2)が実際に成立するかを確認するための検証・テストの基準モデルとして桜音(AIVMX)を用いる。方式・量子化・配信はA8-3を正とする。

## H2. iOSモーニング

iOS AlarmKit検証済み。カスタムAlarmKit音やアプリ内Web Audioループ音はv1対象外。

## H3. Androidモーニング

Android実機のPhase0検証（テスト機1台）で、設定画面表示中を含むfull-screen intentによる疑似着信表示、疑似着信音、通知の`応答`からのAI通話、AI第一声、固定メッセージの通常通話画面と近接消灯まで成立した。近接消灯は固定音声開始後だが従来より早くなり、現段階の機能として採用した。Androidモーニングの機能実装はこの端末で完了とする。音はActivityではなくForeground Service側で鳴らし、全画面表示と音を分離する方針。

ただしこれは1機種でのPhase0結果であり、全メーカーでの動作は未確認。Android 14以降の `USE_FULL_SCREEN_INTENT` 権限が実効的に付与されない場合や、メーカー独自の自動起動・バックグラウンド起動制限により、full-screen intentが出ず通知バナーのみ・無音になる端末が存在しうる。

方針:

モーニングは特定メーカーだけで成立すればよいものではない。

メーカー差で全画面が出ないことを「許容範囲」で済ませない。

full-screen intentの実効付与とメーカー別の自動起動制限は、本番前の要検証・未解決事項として扱い、F7で検証する。

## H4. 疑似電話TTFA

Android実機で STT → LLM → Aivis TTS(クラウド) → 音声再生まで成立し、TTFA約2秒前後を確認した実績は、オンデバイスTTS採用前の履歴としてのみ保持する。このクラウドTTS経路は正式な最終構成には含めない。

その後、TTSはオンデバイス化を採用決定(A8-3)。オンデバイスTTSの実測(POCO X6 Pro / CPU EP 4スレッド、桜音を基準モデルとして計測)は、1文目の再生開始まで約0.9〜1.0秒(文末単位ストリーミング)、INT8化による音質劣化なし。以後のTTFA前提はオンデバイスTTSだけを基準にする。
